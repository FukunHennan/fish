# 登录会话、性能与控制代码维护

日期：2026-09-04。已部署到本机用户级 fish-controller.service。

## 登录会话持久化

登录仍采用原有随机令牌和 14 天有效期。新增用户文件旁的 `.sessions.json`，以 SHA-256 令牌摘要为索引，仅保存用户 ID 与有效期，不保存原始 Cookie 令牌。文件权限 0600，临时文件替换写入。

创建会话保存失败不返回成功登录；退出保存失败会返回错误，避免失效令牌在重启后恢复。账号删除、禁用等现有会话撤销操作随用户保存持久化；过期会话不恢复。保持原有 Cookie 与角色规则，没有延长有效期。

旧版本内存会话无法在这次替换旧进程时迁移，因此本次升级可能需要最后重新登录一次。之后新建立的有效会话可跨重启保留。设备归属与浏览器控制会话仍分开：登录保留不自动恢复鱼的运动。

验证：Go 回归测试覆盖跨实例恢复、退出持久化、过期与撤销失效、磁盘不包含原始令牌；Go 全套测试通过。

## 性能发现

本机 GPU 为 NVIDIA GeForce RTX 3050 Laptop，PyTorch CUDA 可用。原设备选择函数因模型权重初始加载在 CPU，就把配置 GPU 0 改成 CPU，导致实际识别未使用 GPU。现根据 CUDA 可用性选择配置设备，CPU 仅作为不可用时的回退。

模型耗时基准：使用 1035×681 合成黑图，当前模型，先预热，再各测 4 次 predict 调用，GPU 同步计时。测试期间服务仍在运行，结果不是隔离环境基准，也不评价识别准确率。

| 推理设备（0 为 GPU） | 输入尺寸 | 平均耗时 ms |
| --- | --- | --- |
| cpu | 1920 | 1402.3 |
| cpu | 1280 | 643.3 |
| 0 | 1920 | 54.0 |
| 0 | 1280 | 27.6 |

上线后实际处理状态确认设备为 GPU 0，12 个一秒间隔状态样本均值：

| 指标 | 值 |
| --- | --- |
| 采集 FPS | 15.07 |
| 处理循环 FPS | 15.1 |
| YOLO 推理 FPS | 4.33 |
| 服务端帧延迟 ms | 25.72 |

YOLO 提交间隔为 0.2 秒，理论提交上限约 5 次/秒；GPU 的单次耗时不等于实际识别帧率。当前识别只使用用户裁剪区域，没有开启鱼的自动运动。

独立本机 WebRTC 接收端采集 40 帧：632×960，约 15.32 FPS（GPU 修复前的传输基线）。这是本机接收速率，不代表公网速度、浏览器解码耗时或端到端延迟。

设备驱动报告 1920×1080 MJPEG、30 FPS。单采集缓冲时实测约 15.05 FPS，改为 4 帧缓冲约 30.17 FPS，改为 2 帧缓冲约 30.08 FPS，因此采用 2 帧以兼顾吞吐与延迟。短时设置手动曝光 100 未改善单缓冲帧率，测试后恢复自动曝光模式 3 和曝光值 345。

## 控制代码清理

删除 main.jsx 中不再使用的单鱼 sendKeyboardFrame、updateKeyboardControl、旧按键监听依赖、旧状态字段和未使用的 CommandStrip。键盘执行统一由 multiKeyboard.js 承担；选择鱼时按是否启用多鱼控制决定停止旧鱼。运动参数更新改从实际多鱼状态读取当前模式，不再读取已失效的单鱼状态。

不删除仍有调用者的设备状态工具、测试材料或历史原型。前端 38 项测试与生产构建通过。没有向实体鱼发送测试运动命令。
