# 机器鱼系统运行手册

更新日期：2026-10-08

本手册保留 Fish Control 的详细运行行为、账号、赛事、设备控制、视觉、协议、OTA 和诊断说明。文档主导航位于[文档首页](../README.md)；启动、停止与配置范围以[程序首页](README.md)为入口。发生冲突时，以当前代码、自动化测试和实机验收结果为准。

## 1. 项目概览

Fish Control 是一套由现场电脑统一管理多台 ESP32 机器鱼、视觉识别和学生赛事的系统。

```text
浏览器 GUI
   ↓ HTTP / SSE / WebRTC
Go Controller（0.0.0.0:8081）
   ├─ ESP32 机器鱼（WebSocket /ws/device）
   └─ Python Vision（127.0.0.1:8091）
          └─ 摄像头、YOLO、跟踪、循迹和视频
```

核心边界：

- 浏览器不直接连接 ESP32，也不直接访问 Python。
- Go 是登录、权限、设备状态、控制权、命令排队和视觉代理的唯一入口。
- Python 负责摄像头采集、识别、跟踪和视觉控制计算，不直接访问机器鱼 IP。
- 设备在线、手动控制和视觉状态是三个独立概念。
- 设备真实状态以 ESP32 的 `heartbeat`、`state` 和 `command.result` 为准。

## 3. 当前赛事账号

当前 Windows 主机使用账号 `1`（蓝队）、`2`（红队）、`3`（裁判）。账号直接输入数字，不补后缀。账号库路径由 `config/program.json` 的 `FISH_AUTH_USERS` 指定，默认是 Pro1 同级的 `Pro1-runtime/users.json`；相对路径以 Pro1 根目录为基准。运行中的账号库位于项目目录之外；上传脚本读取并校验完整 JSON 后，将同一份数据写入 `controller/.runtime/` 中的账号及设备预约快照。会话令牌哈希及 `.previous` 备份不上传，新电脑需重新登录。新建账号只要求非空、最多 20 个字符且不重复，密码不设长度或格式限制。新登录会撤销同账号旧会话。

| 用途 | 账号 | 页面权限 |
| --- | --- | --- |
| 蓝队 | `1` | 选手端蓝队 |
| 红队 | `2` | 选手端红队 |
| 裁判 | `3` | 裁判端及裁判操作 |


登录赛事首页后会按账号直接进入客户端：`1`、`2` 进入各自的选手端，`3` 进入裁判端。当前席位分配：B1/B2 使用蓝队账号，R1/R2 使用红队账号。服务端对选手页和裁判页都校验账号；直接访问地址也不能跨端进入。第二台机器使用同一账号登录会撤销第一台机器的旧会话，旧页面检测到失效后返回登录界面。

### 3.1 登录模式与安全边界

代码在 `FISH_AUTH_DISABLED` 未设置、为空或为 `true` 时关闭登录校验；当前 `config/program.json` 明确设置为 `false`，本地和公网均启用登录。修改后需重启。进程环境变量优先于 JSON。Go 入口在未设置 `FISH_DEVELOPMENT_MODE` 时默认开启开发模式；认证关闭且未指定比赛状态路径时，会初始化开发比赛。另有 `FISH_TRUST_CF_ACCESS=true` 的 Cloudflare Access 请求头信任模式，启用时需核对上游访问边界。

要在 systemd 环境中覆盖程序配置，可显式设置：

```text
Environment=FISH_AUTH_DISABLED=false
```

如果使用此前部署的 systemd 用户服务，修改服务文件后执行 `systemctl --user daemon-reload && systemctl --user restart fish-controller.service`。重启后还需以实际用户库中的账号登录。

## 4. 启动入口

仓库提供按系统区分的启动脚本。Windows 脚本会构建前端和 Go 控制器，并通过 `watch-controller.ps1` 监督 Go 进程；仅当 `config/tunnel.json` 启用时才启动 Cloudflare Tunnel，届时临时写入 `controller/.runtime/cloudflared.pid` 跟踪隧道。Linux/macOS 脚本构建并以前台方式运行 Go 控制器；Go 负责启动或复用 Python 视觉服务，脚本本身不启动 Cloudflare Tunnel。

Windows：

```bat
scripts\start.bat
```

Linux / macOS：

```bash
bash scripts/start.sh
```

两个脚本都会构建前端和 Go 控制器，并提供 `8081` 正式服务。不要同时运行第二份控制器。

```bash
systemctl --user status fish-controller.service
systemctl --user status fish-cloudflared.service
```

这些 systemd 单元名称来自此前 Linux 部署记录；仓库未提供单元文件，不能仅凭仓库确认它们已安装或开机自启。此前文档还提到 `fish-gui.service`，但正式界面已由 Go 的 `8081` 服务提供，启动前应先核对旧服务是否仍有用途。

此前部署中，`fish-controller.service` 提供 `8081` 正式服务，`fish-cloudflared.service` 提供 Cloudflare 公网入口。实际服务状态需在部署机器上检查。

Windows 开发机使用 `scripts\start.bat` 构建并运行。启动时会尝试注册 `FishStack` 登录启动任务；任务和手动启动都只调用这一入口。再次手动启动时，入口会先接管并关闭上一实例的启动监督窗口、控制器、视觉服务和 Cloudflare Tunnel，确认 `8081` 与 `8091` 释放后只启动一个新实例；不属于本工作区的端口占用不会被强制关闭。`watch-controller.ps1` 在控制器退出后等待 5 秒再启动，包含退出码 0 的情况；关闭启动窗口才会结束监督流程并清理它启动的 Tunnel。任务以当前 Windows 用户登录触发，避免 SYSTEM 账户无法访问用户目录、Python 环境和 Cloudflare 凭据。

前端开发：

```bash
cd controller/frontend
npm run dev -- --host 127.0.0.1
```

生产构建：

```bash
npm --prefix controller/frontend run build
```

构建产物位于 `controller/internal/web/dist` 并由 Go 嵌入。只修改源码或重新构建前端，不会自动替换 systemd 正在运行的 Go 二进制文件。

## 5. 端口与统一参数

| 项目 | 当前值 |
| --- | --- |
| Go Controller | `8081/TCP` |
| 正式前端/API | `8081/TCP` |
| Python Vision | `127.0.0.1:8091/TCP` |
| MJPEG 兼容实现 | 代码保留 `8090/TCP` 参数和服务类，正式视觉服务不启动它；浏览器优先用 WebRTC，失败时轮询 HTTPS JPEG 单帧接口 |
| 局域网发现 | `30303/UDP` |
| 平板遥测 | `9998/TCP` |
| 控制权运动活动期 | `60 s` |
| 视觉运动命令有效期 | `3 s` |
| Go 设备离线判断 | 心跳或连接活动超时 `10 s`，清理任务每 `0.5 s` 检查一次 |
| 设备/控制器心跳 | 约 `1 s` |
| 摄像头采集 | 默认请求 `640×480 YUY2`；不向驱动指定目标帧率。运行时按成功读帧间隔估算帧率，不能由此证明相邻画面均不重复。相机产品资料见[相机手册](../硬件/相机手册.md) |
| YOLO 默认输入 | `1920` |
| 视频优先传输 | WebRTC |

视觉采集在 `config/program.json` 中通过 `FISH_CAPTURE_WIDTH`、`FISH_CAPTURE_HEIGHT`、`FISH_CAPTURE_FOURCC` 设置；`FISH_YOLO_IMGSZ` 调整识别输入尺寸。进程环境变量可覆盖 JSON 值，修改后需重启视觉服务生效。源码注释记录该设备请求 `960×720` 时返回过 `960×540`，因此当前默认使用 `640×480`；现场仍需核对实际协商尺寸和帧率。

相机旋转角度和曝光值统一保存在 `config/program.json` 的 `camera.rotationAngle` 与 `camera.exposure`。裁判端应用旋转会重建预览，但新相机实例会从同一文件恢复曝光值；成功调整曝光也会写回该文件。角度范围为 -180°～180°，曝光实际可调范围由相机驱动决定。手工编辑这两个字段后重新打开预览生效。

## 6. 账号、归属与控制会话

系统分为三层身份：

1. 网页账号：用户、角色和状态。
2. 登录会话：使用 Cookie，在有效期内可跨服务重启。
3. 设备控制会话：由用户 ID、浏览器 `clientId` 和 `deviceId` 共同确定。

归属规则：

- 一名用户可以持有多条鱼。
- 同一条鱼同一时间只能归属一名用户。
- 设备离线、用户退出、运动超时和服务重启会停止运动，但不自动释放归属。
- 服务重启后保留账号归属，不恢复运动；当前浏览器需点击“在本窗口恢复控制”。
- 普通选手租约仍按设备互斥；管理员获取设备时可直接接管旧浏览器租约，服务器会先发送一次停止帧再切换控制者。
- 只有持有者主动释放或管理员强制释放才会解除普通选手归属。
- 管理员全局急停只停止运动，不释放归属。

按键持续按住时，页面约每 15 秒续租。松键、切页或窗口隐藏后停止续租并停止本窗口键盘运动。

## 7. 设备在线与手动控制

状态语义必须严格分离：

- **在线/离线**：只由设备心跳和 Go 快照决定。
- **手动控制可用**：依赖登录、归属、当前浏览器控制会话和设备在线。
- **视觉可用**：只表示摄像头、WebRTC、识别、跟踪是否正常。

没有视觉或视觉连接失败时，不能把在线机器鱼显示为离线，也不能阻断已分配在线机器鱼的手动控制。

手动动作：`forward`、`left`、`right`、`stop`、`idle`。默认频率约 `2.5 Hz`，协议频率范围 `0.3–5.0 Hz`，振幅范围 `0–90°`，偏置范围 `-90°–+90°`。Go 会按每台设备的标定范围限幅，保证完整摆动周期不超过舍机上下限。

多鱼键盘控制可为每条鱼设置独立键位，如 WASD 和 IJKL。相同键位会联动，不同键位可独立操作。

## 8. 视觉、摄像头与视频

视觉流程：

```text
选择服务器摄像头
  → 启动预览
  → 选择 YOLO 模型
  → 识别机器鱼
  → 选择识别目标
  → 绑定物理 deviceId
  → 绘制路径
  → 启动循迹
```

摄像头分为两类：

- **服务器摄像头**：连接在运行 Python Vision 的现场电脑上，用于共享视频、YOLO、跟踪和循迹。电脑自带摄像头如果能被后端打开，也会出现在该列表中。
- **电脑摄像头**：使用当前浏览器的 `getUserMedia`，可选内置或 USB 摄像头，仅供当前页面预览，不代替服务器识别和循迹。

通过 Cloudflare Tunnel 远程访问时，“电脑摄像头”属于访问者所在的电脑，不会自动传回现场 Python。Cloudflare 域名使用 HTTPS，可满足浏览器的摄像头安全环境要求；`localhost` 和 `127.0.0.1` 也属于浏览器允许的本地安全环境。

视频优先使用 WebRTC。浏览器等待 ICE 候选收集完成后才提交 Offer；若连接失败或 12 秒内没有首帧，会自动改用同源 `GET /api/vision/frame.jpg` 的 HTTPS JPEG 轮询。只要视觉服务仍产出新帧，兼容画面可通过 Cloudflare Tunnel 送达。兼容模式将画幅限制在 `smooth`（最高 640×480），每次只发出一个请求；请求或解码超时后会退避重试，短暂失败时保留上一帧，页面重绘后继续取帧。刷新率随网络延迟变化，低于正常 WebRTC；重新打开页面会再次尝试 WebRTC。`smooth`、`hd`、`full` 只改变当前观看连接的分辨率，不改变共享识别原图。公网优先使用 `smooth`。

已登录的选手账号可读取当前视觉会话、获取 WebRTC 配置，通过 `POST /api/vision/webrtc/offer` 建立观看连接，也可在自动降级时读取 `GET /api/vision/frame.jpg?sessionId=...&view=cropped`，无需管理员权限。裁判使用 `view=full`；JPEG 接口仅接受当前会话，并拒绝过期帧。共享摄像头、裁剪和视觉会话设置仍由管理员控制；未登录请求不能访问视觉接口。

管理员可在停止识别和循迹后调整识别区域裁剪。裁剪同时作用于显示和识别，会重建视觉会话，应重新确认目标。裁剪并旋转后的有效画面边界会自动建立场地坐标，不需要四角 ArUco ID 1–4；如有透视畸变，仍可使用手动四点校正覆盖自动坐标。

视觉运动有独立的 3 秒命令有效期。新视觉运动命令续期，设备心跳不续期。超时、手动接管、停止或 OTA 会废止旧视觉会话。

## 9. 赛事系统

比赛形式为蓝队 B1/B2 对红队 R1/R2。裁判控制比赛流程，选手只能控制裁判分配的机器鱼，服务端是比赛状态的唯一权威源。

裁判端的比分和倒计时从服务端比赛状态同步；倒计时在同步间隔内持续更新，暂停后停止。比分按钮按对应的 +10、+2、-2 修改队伍分数，最低为 0。比赛进行中和暂停时仍可编辑赛事名称；比赛时长只能在未进行或未暂停时修改，范围为 00:10–60:00。
比赛结束后的名称和比分更正会同步到已保存的比赛记录。

裁判在“设备管理”中修改归属时，每个席位只能选择一台机器鱼；将设备改到已占用的席位会清除旧设备的页面选择。点击“保存分配”后，页面从服务端重新核对归属再提示成功。换绑或解除分配会撤销相关设备原有的浏览器控制权，选手端按新归属重新取得控制权。

### 9.1 标准流程

1. 裁判签到并绑定 B1/B2/R1/R2 与机器鱼。
2. 完成摄像头、裁剪、曝光、场地坐标和目标识别检查。
3. 裁判开放受限设备试动。
4. 选手分别确认自己的设备正常或异常。
5. 设备确认完成后进入等待开始。
6. 裁判开始比赛前，服务端先确认选手端视频流可录；录像成功启动后才进入 `RUNNING`、开始计时并开放控制。
7. 暂停时服务端立即禁止控制并向已分配鱼发送停止，录像保持连续以保留完整现场过程。
8. 结束时自动封存 H.264 MP4，并把比分、用时、录像地址和真实编码统计写入比赛记录。

### 9.2 状态机

| 状态 | 含义 | 允许选手控制 |
| --- | --- | --- |
| `CHECKIN` | 签到和绑定 | 否 |
| `FIELD_SETUP` | 场地准备 | 否 |
| `TEST` | 设备试动 | 是，受限 |
| `READY` | 等待裁判开始 | 否 |
| `RUNNING` | 比赛进行 | 是 |
| `PAUSED` | 比赛暂停 | 否 |
| `ENDED` | 比赛结束 | 否 |
| `ARCHIVED` | 记录已归档 | 否 |

当前原型计分：进球 `+10`、配合 `+2`、越界/违规 `-2`。这些是当前原型值，正式赛事应以最终竞赛规程为准。

比赛录像直接读取与选手 WebRTC 相同的数据源：相机帧先应用裁判设置的旋转，再应用选手有效区裁剪，然后分别进入 WebRTC 与录像编码器。因此回放与选手比赛时看到的构图一致，不从浏览器录屏，也不补帧。录像保存在 `output/vision/recordings/`；该目录是本机运行数据，不进入 Git。

录像使用真实帧到达时间写入 H.264 MP4。裁判重置未完成比赛时丢弃本场临时录像；正常结束后，比赛记录页通过 `/api/vision/recordings/files/` 自动加载录像，不要求裁判手动选择文件。录像期间禁止修改旋转和有效区，避免同一文件中途改变画面几何。

每次计分后续至少应记录：剩余时间、系统时间、队伍、事件名称、分值变化和 `videoTimestampSeconds`，用于从计分事件精确跳转到录像位置。

断线重连后，前端必须重新获取服务端比赛快照，不能依赖浏览器本地状态恢复比赛。

## 10. 赛事前端方案

当前界面以用户提供的图片为设计文件。验收看相对比例，不锁定绝对像素。顶部导航、左右栏、中央画面、HUD、间距和底部状态条应保持设计稿比例。

正式前端技术路线：原生 HTML/CSS/JavaScript、Vite、SSE/EventSource、WebRTC 和 WebSocket。仓库中的 React 控制台源码保留作历史实验组件，不参与正式构建和正式路由。

后端 API 契约：所有 `/api/*` 响应带 `X-Fish-API-Version: 1` 和 `Cache-Control: no-store`。`GET /api/status` 用于启动检查，返回控制器、在线设备、Python 视觉服务和控制传输状态。正式前端的运动控制只使用长连接 `WS /ws/control`；连接失败时明确报告错误，不自动切换到另一种控制协议。`POST /api/command/realtime` 仅保留为显式后端兼容接口，不由正式前端调用。

日志接口：`GET /api/logs?limit=100` 返回当前诊断会话最新的结构化控制器日志，最多允许读取 500 条，处理器要求管理员身份。认证关闭时所有请求都获得匿名管理员身份，因此不能仅凭接口的管理员检查推断公网日志受到登录保护。每次启动会话还会生成 `controller.jsonl`、`controller.txt`、`python-vision.txt` 和 `runtime.json`，便于排查公网连接、设备注册、控制命令和视觉服务问题。

允许动效：Dock 磁吸放大、卡片悬停轻微放大和浮起、按钮压感、页面淡入/滑入、资源点脉冲、机器鱼悬停高亮和轨迹线轻微流光。动效只用 `transform`、`opacity`、`filter` 和 `box-shadow`，不得改变布局尺寸，并支持 `prefers-reduced-motion`。

正式前端只使用同源相对路径，不在代码中写死本机或局域网 IP。

## 11. 内网穿透与公网访问

正式链路：

```text
远程浏览器
  → Cloudflare Tunnel
  → 现场电脑 Go Controller:8081
  → Python Vision / ESP32 保持在现场
```

此前 Linux 部署记录使用 systemd 用户单元 `fish-cloudflared.service` 管理 Cloudflare Tunnel；Windows `scripts/start.bat` 在 `config/tunnel.json` 启用时从 `controller/.runtime/` 启动 `cloudflared.exe`。两种方式都以 Go `8081` 为应用入口；仓库不能验证当前隧道配置或线上转发规则。

当前 Windows 的 `config/tunnel.json` 配置域名为 `https://fish.chenfukun.space`，目标为现场 Go 控制器 `8081`；实际连通性仍须在部署环境核对。完整设置步骤见[公网访问配置](公网访问配置.md)。

Cloudflare Tunnel 可转发网页、API 和 WebRTC 信令，但不代替 WebRTC 的 ICE/STUN/TURN。跨公网视频不稳定时，可在 `config/program.json` 的 `environment` 中配置以下键：

```text
FISH_WEBRTC_STUN_URL=stun:...
FISH_WEBRTC_TURN_URL=turn:...
FISH_WEBRTC_TURN_USERNAME=...
FISH_WEBRTC_TURN_CREDENTIAL=...
```

前端 Dock、悬停和等比布局均在浏览器本地执行，内网穿透不会改变动效本身。公网主要影响视频延迟、接口响应、命令确认和首次资源加载。

## 12. ESP32 通信协议 v2

设备连接 Go 的 `/ws/device`，所有消息是 UTF-8 JSON，协议版本为 `2`。控制器不再兼容 v1。

### 12.1 注册

Go 先发送：

```json
{"type":"auth.challenge","protocolVersion":2,"nonce":"32位十六进制随机数"}
```

设备使用部署密钥计算 HMAC-SHA256 证明，再发送：

```json
{"type":"register","protocolVersion":2,"deviceId":"A4:CF:12:34:56:78","proof":"64位HMAC","name":"机器鱼1号","firmwareVersion":"2.0.0","ip":"192.168.1.31","capabilities":["motion","ota","battery"]}
```

注册成功前不得执行命令。`nonce` 只用于当前连接，部署密钥不得出现在浏览器、日志或 WebSocket 消息中。

### 12.2 心跳和运动

```json
{"type":"heartbeat","mode":2,"frequency":2.5,"amplitude":28.0,"bias":0.0,"rssi":-52}
```

模式：`0=停止`、`1=待机`、`2=前进`、`3=左转`、`4=右转`。

```json
{"type":"command","requestId":"唯一编号","deviceId":"A4:CF:12:34:56:78","command":"motion.set","payload":{"controlSource":"user-or-vision-bot","mode":"forward","frequency":2.5,"amplitude":28.0,"bias":0.0}}
```

设备必须原样返回 `requestId`：

```json
{"type":"command.result","requestId":"唯一编号","success":true,"message":"OK"}
```

同一设备的手动、键盘、视觉、释放停止和急停必须经过同一发送队列。尚未写入的实时运动可合并，停止必须排在先前已接受的动作之后，且旧命令不能在停止之后再发出。

ACK 语义：`sent` 只表示已写入 WebSocket；`acknowledged` 表示收到对应的 `command.result`；`success` 表示设备报告执行成功；`queued` 只表示实时意图入队，不代表设备已执行。

## 13. 固件、配网与 OTA

默认目标为 Seeed XIAO ESP32-C3，串口波特率 `115200`，当前固件标准版本为 `2.0.0`。设备使用 v2 协议；注册失败达到 3 分钟阈值后进入配网 AP。

设备在服务器注册失败达到 3 分钟时会进入 `Fish-Setup-XXXXXX` 配网热点，并保持 AP，直到用户提交新配置。连接后打开 `http://192.168.4.1/`，可重新设置 Wi-Fi 或上传 XIAO ESP32-C3 的应用固件 `firmware.bin`。不要上传 `bootloader.bin`、`partitions.bin` 或合并镜像。

OTA 只能由管理员发起。设备在下载和写入期间必须停止运动。服务器请求超时不等于 OTA 一定失败，最终结果应以设备重新上线后报告的固件版本为准。

固件编译：

```bash
pio run -d firmware -e seeed_xiao_esp32c3
```

## 14. 诊断与故障排查

每次 Go 启动会在 `controller/diagnostics/runs/` 创建诊断会话：

```text
LATEST.txt
<session-id>/runtime.json
<session-id>/controller.jsonl
<session-id>/controller.txt
<session-id>/python-vision.txt
```

- `runtime.json`：启动环境和进程信息。
- `controller.jsonl`：结构化生命周期和 HTTP 事件，最适合时间线分析。
- `controller.txt`：Go 人类可读日志。
- `python-vision.txt`：摄像头、YOLO、WebRTC 和 Python 运行日志。

复现问题时，一次只复现一类问题，记录操作和大致时间，再取 `LATEST.txt` 指向的完整目录。摄像头重启问题可在同一次运行中重复“打开 → 预览 → 关闭”数次以便对齐时间戳。

`scripts/upload.bat` 在提交前执行 `node scripts/diagnostics/compact-runtime-logs.mjs --apply`：将最新会话之外的原始文件逐字节压缩为 `controller/diagnostics/archives/<session-id>.json.gz`，校验 SHA-256 后删除本地旧原始目录，并重建 `controller/diagnostics/ARCHIVE_INDEX.md`。索引列出每次会话的日志等级、HTTP 错误数、主要异常事件与压缩前后大小。当前会话仍在本机原始目录，推送前检查 `--check` 会阻止未归档的旧会话或损坏的归档。需要原始文件时运行 `node scripts/diagnostics/compact-runtime-logs.mjs --restore <session-id>`，恢复到 `controller/diagnostics/restored/`。录像只保存在本机 `output/vision/recordings/`，不会上传。

常见检查：

```bash
curl http://127.0.0.1:8081/healthz
curl http://127.0.0.1:8091/health
ss -ltnp | rg ':(8081)\b'
查看当前窗口输出即可诊断启动和运行日志。
```

健康接口正常不代表机器鱼在线；设备在线仍以注册和心跳为准。

## 16. 维护规范

- 每次改动尽量只解决一个主题。
- 优先沿用现有模块边界，不在未验证时重写运动和视觉核心链路。
- 不伪造设备状态、传感器数据、OTA 进度、赛事数据或视觉数据。
- 前端的可见状态必须可追溯到后端快照或设备回报。
- 生成输出、诊断记录、模型、校准数据和运行配置不按“无引用文件”随意删除。
- 前端构建会更新 Go 嵌入目录；不要在 Vite 清空输出目录的瞬间并发执行 Go 编译。
- 修改协议、相机、OTA、WebSocket 或硬件控制时，在提交说明中写明自动化测试和实机验收的边界。

## 17. 历史结论与待验证项

已实现并有自动化覆盖的重要改进：

- Go 统一运动限幅、租约校验和单设备出站队列。
- 视觉运动 3 秒有效期与旧视觉会话废止。
- 同一账号不同浏览器不能共用当前控制会话。
- 服务重启保留设备归属，但需当前窗口明确恢复控制。
- 视频预览、服务器识别和每设备视觉工作区的生命周期分离。
- 赛事账号、席位分配和机器鱼在线状态已接入真实后端。
- 比赛开始/结束已接入选手端数据流自动录像，比赛记录页可直接回放服务器 H.264 MP4。

仍需持续实机验收：

- 舍机中位、振幅边界和不同鱼的标定一致性。
- 网络突然中断时的实际物理停机时间。
- Python 崩溃、摄像头失帧、视觉目标丢失和手动接管。
- 多设备并行、跨电脑接管和多账号视觉工作区隔离。
- OTA 失败恢复、离线固件上传和升级后版本确认。
- 公网 WebRTC 的 TURN 配置、延迟和长时间稳定性。
