# 部署与公网访问

## 1. 本机服务

当前电脑端运行三部分：

| 服务 | 地址 | 作用 |
|---|---|---|
| React GUI | `127.0.0.1:8098` | 用户操作界面 |
| Go Controller | `0.0.0.0:8081` | 登录、设备、控制和视觉代理 |
| Python Vision | `127.0.0.1:8091` | 摄像头、YOLO、跟踪和视频 |

浏览器主要访问：

```text
http://127.0.0.1:8098/
```

Go 会自动启动或复用 Python 视觉服务。Python 只监听本机地址，不作为公网入口。

## 2. 启动和停止

Linux / macOS：

```bash
bash scripts/start.sh
bash scripts/stop.sh
```

Windows：

```bat
scripts\start.bat
scripts\stop.bat
```

启动脚本负责 Go 控制器和 Python 视觉服务。当前指定的 `8098` GUI 由 Vite 单独提供：

```bash
cd controller/frontend
npm run dev -- --host 127.0.0.1
```

如果只启动 Go 而没有启动 Vite，后台仍可能正常，但 `8098` 页面不会出现。

手动启动前端开发页面：

```bash
cd controller/frontend
npm run dev
```

前端开发服务器默认使用 `8098`，并把 `/api`、`/healthz` 请求代理到 Go 的 `8081`。

旧的 `gui-redesign-demo` 兼容入口也占用 `8098`，不要与正式入口同时启动；端口被占用时启动会报错，不会自动改用其他端口。Go 自身还在 `8081` 提供构建后的 GUI，供 FRP 转发使用。

若本机已经安装 `fish-controller.service`，由 systemd 管理控制器时使用 `systemctl --user restart fish-controller.service` 重启，不要再运行 `scripts/start.sh` 启动第二份进程。服务的 `ExecStart` 指向已安装的二进制，更新前必须先构建并替换对应文件；仅修改源码不会更新正在运行的服务。`systemctl --user is-active` 只适用于这一部署方式。

## 3. 启动检查

```bash
curl http://127.0.0.1:8081/healthz
curl http://127.0.0.1:8098/healthz
systemctl --user is-active fish-controller.service
ss -ltnp | rg ':(8081|8091|8098)\b'
```

正常时两个健康接口都返回：

```json
{"status":"ok"}
```

## 4. 设备连接路径

```text
ESP32
  └─ 局域网 UDP 发现
       └─ Go 验证 HMAC 并返回控制器地址
            └─ ESP32 建立 /ws/device
                 └─ 注册、心跳、命令、状态
```

ESP32 不需要在网页中填写电脑 IP。设备通过发现响应取得控制器地址。设备使用 MAC 地址作为身份，注册前不能执行命令。

## 5. 网页控制路径

```text
手动控制：浏览器 → Go → ESP32 → 舵机/电机
视觉控制：摄像头 → Python → Go → ESP32 → 舵机/电机
视频显示：摄像头 → Python → Go 视频代理 → 浏览器
```

浏览器不直接连接 ESP32 或 Python。网页收到的设备状态应以 ESP32 后续 heartbeat 和 command.result 为准。

## 6. FRP 公网访问

FRP 的作用是把现场电脑的 Go 入口转发到公网：

```text
远程浏览器 → FRP Server → frpc → Go Controller:8081
```

需要在本机创建被 Git 忽略的配置文件：

```text
config/frpc.toml
```

可从模板开始：

```bash
cp config/frpc.example.toml config/frpc.toml
```

至少修改：

```toml
serverAddr = "真实 FRP 服务端地址"
serverPort = 7000

[auth]
method = "token"
token = "真实 token"

[[proxies]]
name = "fish-controller-web"
type = "http"
localIP = "127.0.0.1"
localPort = 8081
customDomains = ["真实域名"]
```

启动脚本只有在以下条件同时满足时才会启动 `frpc`：

1. 存在 `config/frpc.toml`。
2. 系统中能找到 `frpc`，或设置 `FISH_FRPC` 指向可执行文件。
3. FRP 服务端地址、token、域名和服务端配置正确。

检查：

```bash
ps -ef | rg 'frpc'
cat controller/.runtime/frpc.log
```

没有 `frpc` 进程，或配置仍为示例值时，公网不会通。

## 6.1 Cloudflare 公网访问

如果你用的是 `fish-cloudflared.service`，公网视频卡顿通常不是 HTTP 转发本身，而是 WebRTC 媒体链路在公网下不稳定。

先检查：

- `fish-cloudflared.service` 是否 `active`
- `fish-controller.service` 是否还在运行
- 浏览器视频默认是否停留在 `smooth`

公网视频优先使用 `smooth`。如果 `TURN` 没配好，`hd` 和 `full` 更容易出现卡顿、重连或黑屏。

如果需要跨公网稳定视频，再补：

```text
FISH_WEBRTC_STUN_URL=stun:...
FISH_WEBRTC_TURN_URL=turn:...
FISH_WEBRTC_TURN_USERNAME=...
FISH_WEBRTC_TURN_CREDENTIAL=...
```

## 7. 当前使用范围说明

本项目当前是内部研发和设备调试平台，运行环境默认是受控的局域网或本机环境。现阶段不把公网攻击、商用部署、密钥保护、HTTPS、CSRF、密码存储强化或类似安全加固作为开发目标，也不保留“未来商用/公网部署前检查清单”。相关内容不应阻挡当前设备功能、控制可靠性和视觉效果的完善。

文档中保留 FRP、端口和 WebRTC 的说明，主要用于记录现有运行方式和排查网络连接问题，不代表当前需要建设公网生产系统。

当前应优先关注：

- 设备发现、连接、心跳和真实停机行为。
- 手动控制、视觉控制、控制权切换和发送队列顺序。
- 摄像头采集、目标跟踪、路径规划和视觉控制效果。
- WebRTC/视频连接的稳定性和资源释放。
- OTA 的升级流程、失败恢复和实机验证。
- 多设备并行、服务重启、异常退出和状态恢复。
- 代码、协议参数、运行行为和文档之间的一致性。

OTA 只能由管理员发起。视觉命令停止更新时使用 3 秒有效期；普通手动控制使用 60 秒控制权租约，浏览器正常失焦/松键会主动发送停止。网络突然中断时无法保证浏览器停止请求送达，手动停机可能等待租约到期，不能把视觉 3 秒保护当作所有操作的通用停机时限。实机验收仍需验证断网行为。

## 8. 常见故障定位

| 现象 | 先检查 |
|---|---|
| GUI 打不开 | `8098` 是否监听，前端开发服务是否运行 |
| GUI 打开但接口报错 | `8081/healthz` 和 Go 服务状态 |
| 没有机器鱼 | ESP32 是否联网、发现包、HMAC 和 `/ws/device` 注册 |
| 视频打不开 | `8091` 是否运行、摄像头是否被占用 |
| 公网打不开 | `frpc` 进程、`frpc.log`、域名 DNS、FRP 服务端 |
| 设备突然停止 | 控制器心跳、设备 heartbeat、WebSocket 日志 |

诊断日志默认位于：

```text
controller/diagnostics/runs/
```
