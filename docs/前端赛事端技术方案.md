# 前端赛事端技术方案

更新时间：2026-09-11

本文限定 Fish Control 学生赛事端的前端技术路线、部署边界、动效策略和内网穿透约束。这里描述的是后续 GUI 演进方案，不表示所有能力已经完成；当前实现状态仍应以代码、测试和实机验证为准。

## 1. 目标

赛事端界面面向学生比赛、训练和设备控制，目标是同时满足：

- 视觉按用户提供图片作为设计稿复刻，包含比赛大厅、操控台、自主任务和比赛记录。
- 操控台继续保留真实设备连接、控制权、视频、视觉状态、键盘控制和急停。
- 前端结构可持续维护，便于后续接入任务、积分、回放、策略编程和多鱼协同。
- 正式访问和内网穿透都走同一个 Go Controller 入口，避免前端依赖本机开发端口。

## 1.1 设计稿比例约束

用户提供的图片即当前阶段的设计文件，不作为模糊风格参考处理。前端第一阶段先做静态高保真页面，再接入后端数据和真实控制链路。

附件图片的像素尺寸只用于换算比例，不表示页面必须固定为这些绝对像素：

| 页面 | 参考尺寸 | 主要用途 |
| --- | ---: | --- |
| 比赛大厅 / 首页 | `1685×934` | 换算页面长宽比和模块占比 |
| 操控台 | `1672×940` | 换算页面长宽比、HUD 高度、三栏宽度和场地图比例 |
| 比赛记录 | `1674×940` | 换算页面长宽比、左侧记录栏和右侧积分栏占比 |
| 自主任务 | `1682×935` | 换算页面长宽比、任务栏、策略栏和水池区域占比 |

实现时每个页面应使用对应的设计稿长宽比。页面内部按设计稿的相对坐标、栏宽占比、行高占比、间距占比和层级布局，外层按容器等比适配。不要把图片像素写成不可变的终端尺寸，也不要用普通响应式栅格重新分配比例；响应式只用于等比缩放、滚动兜底和后续移动端单独设计。

第一阶段验收以相对比例为准：顶部导航高度、左右栏宽、中间主画面比例、HUD 高度、卡片间距、右侧状态栏宽度和底部状态栏高度都应与设计稿保持一致。鼠标悬停和 Dock 动效只能使用 `transform`，不得改变设计稿布局占比。

## 2. 限定技术栈

| 层级 | 技术 | 用途 |
| --- | --- | --- |
| 主框架 | React | 页面和组件体系，延续当前正式 GUI 技术路线 |
| 语言 | TypeScript | 约束设备、视觉、比赛、控制和回放数据结构 |
| 构建 | Vite | 开发热更新和生产静态资源构建 |
| 动效 | Motion for React | Dock 磁吸导航、卡片悬停、按钮压感和页面转场 |
| UI 状态 | Zustand | 当前页面、选中设备、操控目标、弹窗和比赛临时状态 |
| 接口状态 | TanStack Query | 登录、任务、记录、固件等普通 HTTP 请求 |
| 实时事件 | SSE / EventSource | 设备状态、控制反馈和视觉状态推送 |
| 视频 | WebRTC | 浏览器低延迟观看链路 |
| 样式 | CSS Modules + 全局主题 CSS | 定制深海科技风视觉，不依赖大型组件库 |
| 水池地图 | DOM + SVG + CSS | 第一阶段稳定实现水池、轨迹、资源点和机器鱼标记 |
| 测试 | Vitest + Playwright | 单元测试、构建验证和关键页面截图检查 |

第一阶段不采用 Next.js、Nuxt、Vue、Svelte、全 Canvas UI、全 Three.js UI、全 PixiJS UI、GSAP 主动画方案或大型后台组件库。PixiJS 只作为二期水池回放增强选项，且只替换水池区域，不替换整套界面。

## 3. 页面范围

顶部主导航限定为四个入口：

- 比赛大厅
- 操控台
- 自主任务
- 比赛记录

设备管理和系统设置保留为页面内按钮入口，不放进主导航。这样可以保持赛事端心智，避免界面退回普通后台管理系统。

## 4. 推荐目录结构

正式源码仍位于 `controller/frontend/src`。后续重构建议收敛为：

```text

├─ main.tsx
├─ app/
```

可运行设计原型放在 `design/gui/prototypes`。该目录用于验证视觉和动效，不应承载真实设备控制逻辑。

## 5. 状态分工

前端状态按来源分层：

- `Zustand`：当前页面、选中设备、当前操控目标、Dock 状态、弹窗、比赛本地临时状态。
- `TanStack Query`：登录信息、固件信息、任务列表、比赛记录、历史回放等普通请求。
- `EventSource`：在线设备、电量、运动状态、控制确认、视觉状态等实时事件。
- `WebRTC`：视频媒体连接状态和观看质量。

不要把所有状态堆在一个 React 大组件中，也不要把所有接口缓存都塞进 Zustand。

## 6. 动效边界

允许的动效：

- 顶部 Dock 磁吸放大。
- 卡片悬停轻微放大和浮起。
- 按钮点击压感。
- 页面切换淡入或轻微滑入。
- 水池资源点脉冲。
- 机器鱼悬停高亮。
- 轨迹线轻微流光。

禁止的动效：

- 视频画面整体漂移、缩放或晃动。
- 急停按钮持续乱闪或位置变化。
- 真实识别框、坐标和控制反馈被装饰动画干扰。
- 鼠标经过导致布局重新排版。
- 大面积粒子、闪光或持续跳动文字影响比赛判断。

所有动效应优先使用 `transform`、`opacity`、`filter` 和 `box-shadow`，避免通过改变宽高、间距或字体大小制造动效。必须支持 `prefers-reduced-motion` 降级。

## 7. 内网穿透边界

正式部署和内网穿透必须走 Go Controller 的 `8081`：

```text
远程浏览器
  → FRP / Cloudflare Tunnel
  → 现场电脑 Go Controller:8081
  → Python Vision 和 ESP32 保持在现场本机或局域网
```

前端不得硬编码 `localhost:8081`、`127.0.0.1:8081`、`127.0.0.1:8091`、`8098`、ESP32 IP 或局域网固定地址。正式代码使用相对路径：

```text
/api/...
/api/events
/api/vision/webrtc/config
/api/vision/webrtc/offer
```

开发时 `8098` 只用于 Vite 热更新，并由 Vite 代理请求到 Go。生产时前端应构建为静态资源，由 Go 的 `8081` 统一提供，供 FRP 或 Cloudflare 转发。

FRP 只能转发网页、API 和 WebRTC 信令入口，不能替代 WebRTC 媒体的 ICE、STUN 或 TURN。公网视频默认使用 `smooth`，需要稳定跨网视频时配置 STUN/TURN，再逐步开放 `hd` 和 `full`。

## 8. 公网体验要求

内网穿透后，前端本地视觉动效基本不受影响；受影响的是视频、设备状态、命令确认和首次资源加载。因此正式界面必须：

- 静态资源同源打包，不依赖外部 CDN。
- 字体、图标和主要视觉资产本地化。
- 操控台显示公网或本地访问状态。
- 视频区域显示 WebRTC 连接、重连、画质和错误状态。
- 控制按钮区分“已点击”、“发送中”、“设备已确认”和“失败/超时”。
- 急停入口固定可见，不参与复杂布局动效。
- 高延迟或公网访问时优先提示使用 `smooth`。

## 9. 实施顺序

1. 在 `design/gui/prototypes` 完成按设计稿相对比例复刻的静态前端 demo。
2. 在正式前端引入 TypeScript、Motion、Zustand 和 TanStack Query 基础设施。
3. 建立赛事端壳子和四个主页面，先使用静态数据复刻图片设计。
4. 完成比赛大厅、操控台、自主任务和比赛记录的静态高保真页面。
5. 确认比例、动效、视觉层级和公网访问静态资源表现后，再接入后端。
6. 将现有真实视频、设备列表、控制权和急停嵌入操控台新布局。
7. 拆分状态和接口层。
8. 执行前端构建、单元测试、截图检查和公网链路验证。

## 10. 验收标准

第一阶段完成时应满足：

- 四个主页面可以切换，布局稳定，不重叠。
- 页面按设计稿相对比例适配容器，主要栏宽、高度和间距占比与图片一致。
- Dock 悬停动效顺滑，但不改变整体排版。
- 深海赛事端视觉接近参考图。
- 操控台保留真实视频、设备状态、运动控制、控制权和急停。
- 正式构建可由 Go `8081` 托管。
- 经 FRP 或 Cloudflare 访问时页面资源、接口路径和视频状态提示正常。

第二阶段完成时应满足：

- TypeScript 类型覆盖核心设备、控制、视觉和比赛数据。
- 状态层、接口层和页面组件边界清晰。
- 可继续接入真实任务、积分、回放和策略部署后端。
