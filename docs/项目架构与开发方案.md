# 机器鱼系统架构与开发方案

更新时间：2026-09-04。本文说明当前仓库实现；“后续方案”不代表已经完成。用户操作见 [多用户控制与视频使用说明](多用户控制与视频使用说明.md)，运行参数见 [项目统一参数](项目统一参数.md)，部署见 [部署与公网访问](部署与公网访问.md)。参数发生冲突时应核对代码和实际运行环境。本项目当前仅面向内部研发和受控环境，暂不以公网攻击防护或商用安全加固为开发目标，工程重点是设备功能、控制可靠性、视觉效果、异常恢复和实机验证。

## 1. 系统范围与边界

系统以 Go 控制器为设备命令和浏览器 HTTP API 入口，管理多台 ESP32 机器鱼；Python 使用服务器连接的一个摄像头完成共享采集、识别和视觉控制计算。React GUI 提供手动、视觉和系统设置页面。

浏览器不直接向 ESP32 发送运动命令；网页用户认证、设备认证和设备控制权是三层不同的检查。Python 产生运动意图，通过 Go 内部接口进入设备发送队列。

HTTP 与媒体边界必须区分：浏览器通过 Go 代理访问 Python API 和 WebRTC 信令；WebRTC 媒体由 Python 与浏览器通过 ICE 协商的连接传输，必要时通过 TURN 中继，并不是普通 Go HTTP 反向代理中的视频字节流。

当前支持一名用户领取多条鱼；共享摄像头和 YOLO 检测之上，为每个“账号 + 浏览器 + 鱼”创建独立视觉控制工作区。

## 2. 进程、入口与目录

| 模块 | 入口及主要源码 | 职责 |
| --- | --- | --- |
| React GUI | `controller/frontend/src/main.jsx`、`VisionPanel.jsx` | 页面、设备选择、按键、视频与操作意图 |
| Go 主进程 | `controller/cmd/fish-controller/main.go` | 配置、诊断会话、发现服务、启动或复用 Python、HTTP 服务 |
| Go Web | `controller/internal/web/` | 账号会话、权限、归属、命令接口、静态资源及视觉代理入口 |
| Go 设备 Hub | `controller/internal/hub/` | 连接注册、设备状态、发送队列、命令结果及视觉期限 |
| Go 支撑模块 | `internal/discovery/`、`identity/`、`visionprocess/`、`visionproxy/`、`diagnostics/` | 发现认证、进程管理、代理和诊断 |
| Python 入口 | `vision/server.py` | Flask/Waitress 服务、共享 VisionService 与 WebRTCServer |
| Python 生命周期 | `vision/service.py`、`session.py`、`web_api.py` | 摄像头目录、视觉会话、动作队列、状态事件和接口 |
| Python 视觉应用 | `tracking_application.py` 继承 `main.py` 的 VisionApplication | 调度采集、识别、渲染、标定和控制 |
| Python 感知与控制 | `perception.py`、`control.py`、`navigation.py`、`control_coordinates.py` | 检测、跟踪、位置估计、坐标映射和运动计算 |
| Python 视频 | `camera_stream.py`、`camera_policy.py`、`crop_region.py`、`webrtc.py` | 摄像头打开、排除规则、裁剪和独立观看连接 |
| ESP32 | `firmware/src/`、`firmware/include/` | 配网、发现、认证、命令执行、遥测、断线停止和 OTA |
| 协议与部署 | `protocol/`、`config/`、`scripts/` | 通信约定、配置模板、开发及部署脚本 |
| 设计材料 | `design/gui/`、`docs/prototypes/` | 历史原型与设计材料，不是正式 GUI 源码 |

正式开发入口是 `controller/frontend`。`gui-redesign-demo` 仍是连接真实后端的兼容入口，不应误当成无设备副作用的模拟环境。

### 端口与网络

| 端口/通道 | 用途 | 边界 |
| --- | --- | --- |
| 8081/TCP | Go API、静态 GUI、ESP32 WebSocket | 正式 HTTP 入口；公网部署另需 HTTPS/访问配置 |
| 8098/TCP | Vite 开发 GUI | 开发入口，API 代理到 Go，不用于替代正式部署 |
| 8091/TCP | Python HTTP API | 仅监听本机回环地址 |
| 30303/UDP | 设备发现 | 局域网发现及 HMAC 证明 |
| 9998/TCP | 视觉平板遥测 | 独立通道，是否开放应按实际部署核查 |
| WebRTC ICE 协商通道 | 视频媒体 | 直连或 TURN；仅转发 8081 不保证公网媒体可达 |

浏览器生产视频仅使用 WebRTC。仓库保留 MJPEG 实现和测试，但不是当前 GUI 的自动回退链路。

## 3. 启动与设备接入

Go 主程序读取项目配置并创建诊断目录，解析 Python 运行环境，启动或复用本机视觉后端，随后启动发现和 HTTP 服务。Python 管理器仅关闭其拥有的子进程；不能把复用外部服务理解为完整的进程托管。

设备链路为：ESP32 配网联网 → UDP 公告与控制器响应 → HMAC 校验 → 建立 `/ws/device` → `auth.challenge` → 带证明的注册 → 注册成功 → 心跳、状态和命令结果。

MAC 格式的 `deviceId` 标识物理设备，IP 只是当前网络地址。发现证明和 WebSocket 注册使用各自的认证域；网页登录账号不能代替设备证明。

## 4. 账号、归属和控制会话

### 三种身份

| 身份 | 标识 | 生命周期 |
| --- | --- | --- |
| 网页账号 | 用户 ID、角色、状态 | 用户数据持久化 |
| 登录会话 | 服务端会话及浏览器 Cookie | 令牌摘要持久化；有效期内重启可继续登录 |
| 设备控制会话 | 用户 ID + 浏览器 `clientId` + `deviceId` | 当前页面生成 clientId；刷新/换窗口需恢复控制 |

角色包括普通用户与管理员。管理员可执行账号管理、全局急停和强制释放等专属操作，但普通运动请求仍须取得当前设备的浏览器控制会话。

### 归属状态转换

- 空闲 → 用户明确领取 → 账号拥有归属，当前浏览器可控制。
- 同一用户领取另一条鱼 → 原鱼归属保留，新增鱼也归该用户。
- 超时、设备离线或用户退出 → 停止相应运动，归属不自动释放。
- 服务重启 → 恢复账号归属，清空浏览器会话标识，不恢复运动。
- 持有者点击“在本窗口恢复控制” → 新窗口获得控制会话，旧窗口命令被拒绝。
- 持有者主动释放或管理员强制释放 → 停止并解除归属。

全局急停停止运动但保留归属。前端 `leaseIsMine` 必须同时匹配用户 ID 和非空的当前 clientId；账号拥有鱼不代表当前浏览器已经能发命令。

`/api/leases`：POST 领取/恢复，PATCH 校验并刷新现有活动期限，DELETE 释放。普通停止也不能跨用户或跨浏览器干扰他人的控制会话。管理员全局急停使用独立接口。

归属数据保存到用户数据文件旁的 `.reservations.json`；运动活动期限的字段仍名为 `expiresAt`，不能据此宣称账号归属到时释放。超时回调停止一次并标记运动过期，后续持有者操作可以刷新活动期限。

## 5. 手动命令链路

浏览器按键/按钮 → Go 用户权限 → 设备归属与 clientId 校验 → 参数与舵机几何限制 → 每设备发送队列 → ESP32 执行 → 结果/状态上报 → GUI 更新。

普通命令和实时键盘接口的确认语义不同：

| 结果 | 含义 |
| --- | --- |
| 实时接口 `queued=true` | Go 接受入队，不证明已经执行 |
| 普通接口 `acknowledged=true` | 收到关联请求的设备结果，还需检查 success |
| 设备 `heartbeat/state` | 设备最近上报的实际状态，不是持续动作承诺 |

`multiKeyboard.js` 为每条鱼维护独立命令队列。当前选中鱼或已启用多鱼键盘控制的鱼，必须先由本窗口领取，才接受对应按键。配置相同按键意味着联动；不同按键组用于独立控制。窗口失焦或切到后台会停止本窗口键盘运动。

释放、换控制会话和视觉失效要与队列停止/清理保持顺序，防止旧命令在新控制者之后执行。具体队列语义以 Hub 的实现和生命周期测试为准。

## 6. 视频与识别链路

服务器摄像头 → 采集线程最新帧 → 共享裁剪 → 预览或感知处理 → 渲染画面及状态 → WebRTC 最新帧缓冲 → 各观看连接独立缩放/编码 → 浏览器。

### 采集和推理

当前默认采集 1920×1080、请求 30 FPS、MJPEG；YOLO 输入尺寸为 1920。服务环境变量 `FISH_CAPTURE_WIDTH`、`FISH_CAPTURE_HEIGHT`、`FISH_YOLO_IMGSZ` 可覆盖默认值，重启后生效。YOLO 内部仍可能按模型尺寸对齐和等比例处理。

单缓冲现场曾测得约 15 FPS；改为双缓冲后，同一设备独立采集实测约 30.08 FPS。请求值仍不能替代运行服务指标，摄像头采集、处理循环、YOLO 推理和浏览器播放帧率必须分开记录。

项目按名称排除 USB2.0 FHD UVC WebCam，保留 Global Shutter Camera，不能固定认为设备编号 0 永远是同一摄像头。驱动提供的超大输出模式不能作为传感器原生像素证据；实物型号与用户提供规格表的一致性仍需核实。

### 每用户观看质量

WebRTC 的 smooth、hd、full 分别限制在 640×480、1280×960、1920×1440 边界内，保持比例、不放大小图。对于 16:9 原图，实际输出高度相应缩小。这些是每个连接的观看设置，不修改共享识别原图。当前是手动选择，不是自适应码率/分辨率系统。

浏览器关闭本机预览不删除共享采集会话。前端缓存连接、重试和服务端媒体轨道具有各自生命周期；切换观看质量可能短暂重建媒体连接。

### 裁剪与坐标

裁剪使用相对原始图像的归一化矩形，保存在服务器。管理员在停止识别/循迹后应用裁剪，后端重建预览会话，不恢复旧目标控制。显示和感知使用同样的裁剪图像，逻辑宽高同步调整。

浏览器点击按实际显示区域及视频比例映射回裁剪后的逻辑坐标；不能直接拿客户端传输尺寸当作识别坐标。重复框选相对现有裁剪组合。裁剪后应重新确认目标及场地/方向标定；裁剪不是透视矫正。

`TrackingVisionApplication` 在没有场地单应矩阵时提供画面坐标映射，有场地标定时使用相应映射。不能将未标定的画面坐标当作真实物理测量。

## 7. 视觉控制及隔离边界

YOLO/跟踪 → 目标与参考位置 → 坐标映射/路径/方向 → 控制计算 → Go `/api/vision/device-command` → Hub → ESP32。

浏览器通过 Go 进入设备视觉工作区。Go 根据登录用户、浏览器 `clientId` 和设备归属覆盖身份头；Python 将这组身份附在内部运动命令中，Go 在命令入队前再次核对当前租约。

目前应明确承认的边界：

- 根 VisionService 管理共享摄像头和检测；设备工作区各自保存目标、路径、方向与控制状态。
- 同一识别编号不能同时绑定给两个活动工作区；同一设备的新控制浏览器会终止旧工作区。
- 摄像头、识别、曝光和裁剪属于共享设置，写操作由管理员控制；观看连接和工作区状态相互独立。
- 工作区目前保存在进程内存中，服务重启后需重新确认目标、路径和方向标定。
- 临时跟踪编号与物理设备 ID 不同，丢失重现可能换号；稳定身份恢复尚未完成。

## 8. 超时、错误与恢复

| 机制 | 当前行为 | 不应混淆为 |
| --- | --- | --- |
| Go/固件设备心跳超时 | 约 3 秒，断连/停止保护 | 用户归属过期 |
| 手动租约活动期限 | 默认 60 秒，过期停止但保留归属 | 自动开放给其他用户 |
| 视觉运动期限 | 常规视觉运动约 3 秒，失效停止并废止旧会话命令 | 设备心跳即可续命 |
| 采集新鲜度保护 | `CAMERA_STALE_TIMEOUT_S` 默认 0.35 秒，循环按帧率设下限 | 视频播放容忍时间 |
| WebRTC 等帧 | 一次 1 秒无帧继续等待，不立即结束轨道 | 摄像头必然断开 |
| WebRTC 画面年龄 | 观看端允许至 2 秒，超出丢弃 | 放宽运动安全期限 |
| 浏览器短暂 disconnected | 保留 5 秒恢复窗口；failed 进入重连 | 恢复控制权 |

会话过期、撤销或旧版本升级导致登录失效时，前端应重新检查账号状态并进入登录流程，不继续用旧视觉数据报“摄像头不可用”。网络问题、采集错误、推理错误和权限拒绝应分别显示和记录。

## 9. 状态保存与恢复

| 状态 | 保存位置/归属 | 恢复限制 |
| --- | --- | --- |
| 账号 | `FISH_AUTH_USERS` 指定位置或用户配置目录 | 不在文档中记录密码/密钥 |
| 登录会话 | Go 内存及用户文件旁 `.sessions.json`（令牌摘要） | 原有 14 天有效期；退出/撤销后不恢复 |
| 鱼的用户归属 | 用户文件旁 `.reservations.json` | 只恢复归属，不恢复浏览器运动会话 |
| 按键与手动参数 | 浏览器 localStorage，按账号分组 | 不跨电脑同步 |
| 裁剪 | `CACHE_DIR/camera-crop.json` | 服务器共享，不是个人显示设置 |
| 模型及视觉标定材料 | `vision/assets/` 与对应配置路径 | 切摄像头、裁剪后需检查适用性 |
| 设备/命令/视觉运行状态 | Go/Python 内存及设备上报 | 不以旧界面缓存替代新状态 |
| 诊断记录 | `controller/diagnostics/runs/` | 保留运行记录，注意脱敏 |

## 10. 部署、验证与开发顺序

前端源码修改 → 前端测试/构建 → Go 构建（嵌入新 dist）→ 备份现有二进制 → 更新运行服务 → 检查健康接口及实际功能。只执行 npm build 不会更新正在运行的 Go 二进制；Python 源码变化也要由新进程加载。

当前本机使用用户级 `fish-controller.service`；执行路径以 `systemctl --user show` 为准，不把本机路径当作所有部署环境的固定路径。纯文档修改不重启服务。

验证入口：

- Go：`cd controller && go test ./...`，重点是控制生命周期、多用户归属、运动限制和视觉期限。
- 前端：`npm --prefix controller/frontend test` 与 `npm --prefix controller/frontend run build`。
- Python：使用 `vision/.venv/bin/python`，设置 `PYTHONPATH=vision` 后运行相关 unittest；视频、裁剪、API、坐标与感知测试按改动范围选择。
- 现场：单独验证相机真实帧率、持续推理、两账号两设备并发、断网恢复、识别丢失及公网媒体。单元测试通过不等于这些现场测试完成。

后续开发建议按依赖推进：先建立用户/设备/识别目标绑定与权限模型，再拆分每鱼视觉任务，随后实现稳定目标恢复和客户端状态隔离；最后做并发、负载及公网长时间验证。图像分辨率调整不能代替跟踪身份修复，延长视频容忍也不能代替网络问题定位。

登录持久化不保存原始 Cookie 令牌，文件权限为 0600，使用临时文件和替换写入；退出持久化失败返回错误，避免宣称已退出但重启后恢复。浏览器控制 clientId 仍在重启后清空：保持登录不代表自动恢复设备运动。
