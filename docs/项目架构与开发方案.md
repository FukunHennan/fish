# 机器鱼系统架构与开发方案

## 1. 建设目标

在 Windows 局域网电脑上运行中央控制器，通过一个网页完成机器鱼管理、运动控制、RERVISION USB 摄像头视觉处理和全部视觉操作。后期通过 FRP 暴露同一网页，远程用户不使用另一套界面。

## 2. 总体架构

```text
浏览器（局域网或 FRP）
        │ HTTP / WebSocket / 视频流
        ▼
Go 中央控制器（唯一对外入口）
  ├─ React/Vite 网页
  ├─ 登录、设备管理和状态汇总
  ├─ ESP32 发现、认证与指令转发
  ├─ Python 视觉进程启动、停止和监控
  └─ 视觉接口及视频流反向代理
        │                         │
        │ WebSocket               │ 本机内部接口
        ▼                         ▼
ESP32 机器鱼                Python 视觉服务
尾舵机控制、状态上报         RERVISION、YOLO、OpenCV、循迹
```

浏览器不直接连接机器鱼或 Python。Go 是局域网和 FRP 的统一入口。ESP32 使用 MAC 地址作为身份，结合共享部署密钥进行 HMAC-SHA256 动态挑战认证。

## 3. 网页功能

- 显示在线机器鱼的 MAC、IP、固件、信号、运行时间和运动状态。
- 控制前进、左转、右转、待机、停止及尾舵频率、振幅、偏置。
- 枚举并下拉选择 RERVISION 摄像头。
- 启动、停止和监控 Python 视觉服务，显示错误、FPS 和识别状态。
- 显示带 YOLO、轨迹、标定点和 HUD 的处理后视频。
- 在视频画布上完成场地四点标定、鱼尾框选、鱼头方向标定、轨迹绘制和清除。
- 复现启动/停止循迹、转圈测量、录像、截图、曝光、CLAHE 等现有视觉功能。
- 保留 OTA 接口，后续逐步加入固件上传、校验、升级进度和结果显示。

不再使用 OpenCV 本地操作窗口，网页是唯一正式操作入口。浏览器坐标按视频原始尺寸换算后传给 Python，保证不同屏幕尺寸下标定和轨迹坐标准确。

## 4. 通信与数据流

- **设备发现：** ESP32 联网后主动向所在子网广播带 HMAC 证明的设备信息；Go 验证后单播回复，ESP32 从回复源地址自动取得电脑 IP 并建立 WebSocket。用户只需配置 Wi-Fi，无需填写控制器地址。
- **设备控制：** 浏览器 → Go → ESP32 WebSocket；ESP32 执行后上报最新状态。
- **视觉控制：** 浏览器通过 Go 的 WebSocket 发送画布事件和工具命令，Go 转发给本机 Python 服务。
- **视频：** Python 生成处理后画面，Go 反向代理给网页。初版使用现有 MJPEG；如果 FRP 下延迟或带宽不满足要求，可替换为 WebRTC，页面和控制协议不变。
- **安全停止：** 控制器断线、视觉失帧、目标丢失、视觉超时、进程退出或 OTA 请求均使 ESP32 尾舵回到 90°并停止摆动。

## 5. 目录规划

```text
fish/
├─ controller/        Go 中央控制器
│  ├─ cmd/            程序入口
│  ├─ internal/       设备、认证、视觉进程、接口和视频代理
│  └─ frontend/       React/Vite 网页
├─ firmware/          ESP32 固件
├─ vision/            Python 无窗口视觉服务和模型资源
├─ config/            部署配置（密钥不提交）
├─ protocol/          ESP32 与视觉通信协议
├─ scripts/           构建和部署脚本
└─ docs/项目架构与开发方案.md
```

## 6. 开发阶段

1. **ESP32 基础功能：** 联网、发现认证、状态上报、尾舵控制和安全停止。
2. **网页设备控制：** 显示设备信息并完成全部运动指令。
3. **网页视觉整合：** Python 无窗口化、摄像头选择、进程管理、视频和视觉状态接入。
4. **网页完整视觉操作：** 迁移标定、轨迹、循迹、录像、截图和全部现有工具。
5. **UI 与部署：** 统一界面设计、Windows 打包、登录权限、HTTPS、FRP 和 OTA 完善。

## 7. FRP 与安全要求

FRP 只转发 Go 服务端口，局域网和远程访问使用同一网页。正式开放公网前必须增加网页登录、会话认证、HTTPS、控制权限和操作日志；设备部署密钥不得发送给浏览器。紧急停止接口应始终处于最高优先级。

## 8. 可行性结论

项目可行。现有 ESP32 控制链路已经能完成动态认证、状态显示和安全指令；现有视觉程序已经具备 RERVISION/OpenCV/YOLO、MJPEG、标定、循迹、录像和截图能力，可以复用算法并把界面操作改为 Web 接口。

主要工作量在 Python 无窗口化、浏览器画布事件协议、Go 视觉进程管理和公网安全。主要风险是 MJPEG 经 FRP 的带宽与延迟、摄像头索引变化、浏览器坐标换算和远程误操作；上述风险均有明确解决方式，不构成架构阻碍。

## 10. 视觉启停与画布操作边界

网页中的“停止视觉”不是只隐藏画面。正常关闭顺序为：

1. 网页发送 `system.stop`，让视觉控制先进入安全停止。
2. 网页调用 `/api/vision/stop`。
3. Python 请求视觉主循环退出并等待工作线程结束。
4. 关闭 MJPEG 服务、目标检测器、摄像头、平板通信和录像文件。
5. Go 返回 `stopped`；网页移除 MJPEG `<img>` 并禁用全部画布和视觉工具。

停止后，场地标定、鱼尾框选、鱼头方向、轨迹绘制、截图、录像、曝光、CLAHE 和循迹操作均不再接受。停止前尚未处理的画布事件会被清空，避免重启视觉后执行旧轨迹。磁盘上已经保存的鱼尾模型、转圈标定结果、录像和截图不删除。

运行期间再次点击当前高亮的画布工具会关闭该工具。场地标定、鱼尾标定和鱼头方向在关闭时必须向 Python 发送同一切换事件，使网页状态与运行时选择状态同步；轨迹绘制没有独立的 Python 选择模式，关闭时只需清除网页工具状态。

当前自动测试覆盖：视觉启动/重复启动、动作校验、停止状态、停止回调、停止后拒绝动作，以及停止再启动时不复用旧画布事件。真实摄像头是否被驱动完全释放、USB 驱动是否能立即重新打开，仍属于整机验收项目，应在目标 Windows 电脑上连续执行至少 20 次“启动→划线→停止→重启”。

## 11. 视频卡顿分析与调优顺序

当前视频链路为 Python 处理画面 → 960×540 JPEG → 最高 30 FPS MJPEG → Go 反向代理 → 浏览器。默认 JPEG 质量为 50。这个方案开发简单，但有以下特征：

- MJPEG 每帧独立压缩，不利用前后帧差异，带宽显著高于 H.264/WebRTC。
- 每个观看者当前独立执行 JPEG 编码；多标签页或多人观看会线性增加 CPU 开销。
- 无线网络和 FRP 抖动会表现为停顿或延迟累积。
- YOLO 按约 0.2 秒间隔提交推理，视觉主循环仍需完成跟踪、绘制和视频缩放。
- 录像写入虽然使用独立线程，但磁盘跟不上时仍会丢弃录像帧。

排查必须先区分处理慢、编码慢和网络慢：

1. 只保留一个本机浏览器观看者，关闭录像、CLAHE 和循迹。
2. 比较摄像头测得 FPS、视觉循环 FPS、YOLO FPS 和浏览器观感。
3. 在局域网内直接访问 Go，排除 FRP；再比较远程结果。
4. 如果本机也卡，优先降到 640×360、15–20 FPS；如果本机流畅而远程卡，优先降低码率或改用 WebRTC/H.264。
5. 同时观看人数超过 1 时，应先改为“每帧只编码一次、所有客户端共享编码结果”，再提高人数上限。

建议近期默认值先采用 640×360、20 FPS、JPEG 质量 45–55 做现场对比测试，并记录端到端延迟。没有测量结果前不直接替换 WebRTC；如果 FRP 环境持续无法满足控制延迟，再保持现有控制接口不变，仅替换视频传输层。
