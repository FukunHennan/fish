# Fish 项目维护计划

## 维护目标

当前阶段优先保证现有功能稳定、代码边界清晰、参数定义一致。维护期间默认不修改已经工作的设备通信协议，不在未验证的情况下重写运动控制和视觉控制核心链路。

## 当前模块边界

- `firmware/`：ESP32-C3 固件、舵机控制、网络与 OTA。
- `controller/`：Go 控制器、设备状态、Web API、React 前端。
- `vision/`：相机、YOLO、方向估计、路径循迹、控制坐标映射。
- `design/`：独立 HTML 设计稿，不承担生产逻辑。
- `scripts/`：启动、停止、上传脚本。
- `protocol/`：设备与控制器之间的协议定义。

## 第一阶段：低风险维护

1. 清理根目录孤立文件和失效入口。
2. 保持 `scripts/` 只包含当前实际使用的启动流程。
3. 清理未使用 import、重复 helper 和过期兼容代码。
4. 所有纯计算逻辑优先抽成独立模块，并配套单元测试。
5. 不伪造设备状态、传感器数据、OTA 进度或视觉数据。

## 第二阶段：前端结构整理

`controller/frontend/src/main.jsx` 目前负责页面组合、设备状态和控制协调；设备栏、手动检查器、视觉面板、设置工作区和账户管理已经拆出。后续继续把接口请求和页面状态拆成：

```text
src/
├─ App.jsx
├─ pages/
│  ├─ VisionPage.jsx
│  ├─ MotionCalibrationPage.jsx
│  └─ MaintenancePage.jsx
├─ components/
├─ motion/
├─ vision/
└─ api/
```

当前目录仍保留既有入口结构，拆分必须保持现有 API 行为不变，并在每一步执行前端测试和构建。

## 第三阶段：运动标定参数统一

统一每条机器鱼的 `MotionCalibrationProfile`，由 Controller 按 `deviceId/MAC` 持久化。React、Go、Vision 和 Firmware 使用同一语义：

```text
servoMin
servoMax
straightCenter
forwardFrequency
forwardAmplitudePercent
leftCenterRatio
leftFrequency
leftAmplitudePercent
rightCenterRatio
rightFrequency
rightAmplitudePercent
transitionMs
```

旧的 `frequency / amplitude / bias` 仅作为兼容下发层，不应继续成为新的标定数据模型。

## 第四阶段：视觉链路收口

普通循迹流程固定为：

```text
单鱼识别 → 方向确认 → 绘制轨迹 → 启动循迹
```

场地 Homography 作为可选测量能力，不再作为普通循迹前置条件。默认使用 IMAGE 控制坐标；存在有效场地标定时，可切换 FIELD 坐标用于真实距离、速度和转弯半径测量。

## 修改规则

- 每次维护尽量只解决一个主题。
- 修改现有文件前读取最新 SHA。
- 不在同一次提交里混合无关重构和功能变更。
- 优先补测试，再做结构调整。
- 涉及硬件控制、相机、OTA、WebSocket 的改动必须注明是否完成实机验证。
- 无实机验证时只能声明代码级检查或自动化测试结果。

## 当前建议顺序

2026-09-04 代码审查后，优先处理控制可靠性，再进行前述结构整理：

1. 舵机角度限幅：已修复 Go 对显式偏移及视觉向前标定的范围检查，已补回归测试；待实机验证，并核对设备中位与控制器标定一致。
2. 视觉中断停机：已加入 Go 侧独立的 3 秒运动命令有效期、向前标定定时停止、过期排队命令丢弃和 WebSocket 写入超时。自动化测试覆盖免登录/认证模式、持续设备心跳、丢失 ACK、命令续期与手动接管；待实机验证。
3. 租约过期停机：已统一清理回调，在租约锁内先入队停止，再接受新控制；回归测试覆盖所有清理入口。
4. 控制接管：已绑定浏览器标识，接管时重置序号并清理旧运动；旧浏览器不能续发运动或通过停止抬高新浏览器序号。视觉控制要求显式启动，超时和接管后废止旧会话。
5. 文档同步：已纠正认证默认值、统一开发端口，并明确手动租约与视觉超时的不同保障；历史设计仍作为目标和背景，不作为当前验收结果。
6. 实机验收：验证偏移边界、Python 中断、断网、释放控制权和跨电脑接管。
7. 完成上述工作后，再进行目录清理、前端拆分和高级功能开发。
