# Fish 项目维护计划

## 维护目标

当前阶段优先保证现有功能稳定、代码边界清晰、参数定义一致。维护期间默认不修改已经工作的设备通信协议，不在未验证的情况下重写运动控制和视觉控制核心链路。

## 当前模块边界

- `firmware/`：ESP32-C3 固件、舵机控制、网络与 OTA。
- `controller/`：Go 控制器、设备状态、Web API、React 前端。
- `vision/`：相机、YOLO、方向估计、路径循迹、控制坐标映射。
- `design/`：独立 HTML 设计稿，不承担生产逻辑。
- `scripts/`：启动、停止、上传脚本。
- `protocol/`：设备与控制器之间的协议定义。

## 第一阶段：低风险维护

1. 清理根目录孤立文件和失效入口。
2. 保持 `scripts/` 只包含当前实际使用的启动流程。
3. 清理未使用 import、重复 helper 和过期兼容代码。
4. 所有纯计算逻辑优先抽成独立模块，并配套单元测试。
5. 不伪造设备状态、传感器数据、OTA 进度或视觉数据。

## 第二阶段：前端结构整理

`controller/frontend/src/main.jsx` 已承担设备列表、手动控制、运动标定、OTA、设备设置等多项职责。后续逐步拆成：

```text
src/
├─ App.jsx
├─ pages/
│  ├─ VisionPage.jsx
│  ├─ MotionCalibrationPage.jsx
│  └─ MaintenancePage.jsx
├─ components/
├─ motion/
├─ vision/
└─ api/
```

拆分必须保持现有 API 行为不变，并在每一步执行前端测试和构建。

## 第三阶段：运动标定参数统一

统一每条机器鱼的 `MotionCalibrationProfile`，由 Controller 按 `deviceId/MAC` 持久化。React、Go、Vision 和 Firmware 使用同一语义：

```text
servoMin
servoMax
straightCenter
forwardFrequency
forwardAmplitudePercent
leftCenterRatio
leftFrequency
leftAmplitudePercent
rightCenterRatio
rightFrequency
rightAmplitudePercent
transitionMs
```

旧的 `frequency / amplitude / bias` 仅作为兼容下发层，不应继续成为新的标定数据模型。

## 第四阶段：视觉链路收口

普通循迹流程固定为：

```text
单鱼识别 → 方向确认 → 绘制轨迹 → 启动循迹
```

场地 Homography 作为可选测量能力，不再作为普通循迹前置条件。默认使用 IMAGE 控制坐标；存在有效场地标定时，可切换 FIELD 坐标用于真实距离、速度和转弯半径测量。

## 修改规则

- 每次维护尽量只解决一个主题。
- 修改现有文件前读取最新 SHA。
- 不在同一次提交里混合无关重构和功能变更。
- 优先补测试，再做结构调整。
- 涉及硬件控制、相机、OTA、WebSocket 的改动必须注明是否完成实机验证。
- 无实机验证时只能声明代码级检查或自动化测试结果。

## 当前建议顺序

1. 仓库卫生与过期文件清理。
2. 抽离前端纯计算 helper。
3. 拆分 `main.jsx` 页面职责。
4. 统一 MotionCalibrationProfile。
5. Vision 读取同一运动标定配置。
6. Firmware 原生支持过渡时间和停止回直行中心。
7. 最后再继续增加新的高级功能。
