# Web 视觉工作区重构设计

**状态：** 待用户复核  
**日期：** 2026-08-25  
**范围：** React 网页、Go 视觉代理、Python 视觉服务  
**不包含：** YOLO 模型重训、机器鱼运动协议重构、多目标控制、WebRTC 首次落地

## 1. 背景与问题

当前 MJPEG 帧仍包含旧 OpenCV 工具栏和大量 HUD。浏览器只能把这些内容当成图片像素，因此画面底部的“启动、停止、标定、录像、截图”等按钮无法点击；网页外部同时存在另一套按钮，造成重复界面和状态混乱。

当前视频与视觉处理还共用一个粗粒度的 `running/stopped` 状态。摄像头枚举成功不代表能够稳定读取首帧；视觉线程异常退出后，网页可能继续显示“运行中”，视频不断重连，画布事件仍能提交但无人处理。摄像头选择、视频连接、视觉算法、画布工具和控制会话没有共同的会话身份。

## 2. 设计目标

1. 视频帧只包含摄像头内容、算法检测结果和必要的机器视觉叠加，不包含可交互工具栏。
2. 摄像头预览与视觉算法运行分离：先确认正确视频源，再启动检测或循迹。
3. 标定点、鱼尾框、鱼头方向和轨迹由网页覆盖层即时绘制。
4. 所有动作都有明确的接受、完成或失败结果，网页不再只显示“已提交”。
5. 视频、算法或摄像头异常时，服务端和网页收敛到同一状态并禁用不安全操作。
6. 停止会话后释放摄像头、关闭视频连接、停止循迹并清空未处理画布事件。
7. 保留现有 YOLO、标定、导航和机器鱼视觉控制算法。

## 3. 非目标

- 第一轮继续使用 MJPEG，不同时引入 WebRTC。
- 不在本次重构中支持多摄像头同时显示。
- 不支持多条机器鱼同时进行视觉闭环。
- 不把 Python 视觉算法迁移到浏览器或 Go。
- 不恢复 OpenCV 本地工具栏作为正式入口；本地调试窗口可保留在显式调试模式中。

## 4. 总体结构

```text
React 视觉工作区
  ├─ 摄像头选择与预览控制
  ├─ Canvas/SVG 交互覆盖层
  ├─ 算法与循迹控制
  └─ 状态、指标和错误面板
           │ HTTP + MJPEG
           ▼
Go 中央控制器
  ├─ 同源 API
  ├─ 视频反向代理
  └─ 视觉进程健康状态转换
           │ 仅本机 HTTP
           ▼
Python 视觉服务
  ├─ 摄像头会话与首帧验证
  ├─ 原始/处理后视频发布
  ├─ YOLO、标定、轨迹与循迹
  └─ 操作结果和状态快照
```

浏览器仍不直接访问 Python。Go 是唯一的网页入口，Python 继续只监听回环地址。

## 5. 状态模型

视觉服务使用以下状态，而不是单一 `running`：

| 状态 | 含义 | 视频 | 画布工具 |
|---|---|---|---|
| `idle` | 没有摄像头会话 | 无 | 禁用 |
| `opening` | 正在打开设备并等待首帧 | 无 | 禁用 |
| `previewing` | 摄像头稳定输出，仅预览 | 有 | 禁用 |
| `processing` | 视觉算法运行 | 有 | 标定和轨迹工具可用 |
| `tracking` | 视觉闭环正在控制机器鱼 | 有 | 编辑工具锁定，停止可用 |
| `stopping` | 正在安全停止并释放资源 | 即将关闭 | 禁用 |
| `error` | 启动或运行失败，资源已回收 | 无 | 禁用 |

合法转换：

```text
idle → opening → previewing → processing → tracking
  ▲        │          │            │          │
  └────────┴──────────┴────────────┴──────────┘ stop
           └────────── error ────────────────→ idle/retry
```

任何状态收到紧急停止都必须先停止机器鱼，再释放视觉资源。只有 `previewing` 或 `processing` 可以切换为正常停止；`tracking` 必须先结束视觉控制会话。

## 6. 会话身份

每次成功打开摄像头后，Python 生成不可预测的 `sessionId`。状态、视频地址、画布动作和算法操作都必须携带该会话 ID。

- 新会话建立后，旧会话的事件、视频请求和算法结果失效。
- 停止时清空未处理事件。
- 浏览器收到不同 `sessionId` 后必须清空本地覆盖层和重连计数。
- Python 拒绝缺失、过期或不匹配的会话请求，返回 `409 session_mismatch`。

## 7. 摄像头枚举与预览

枚举结果不能只依赖 `VideoCapture.isOpened()`。每个候选设备必须：

1. 尝试打开指定后端和索引。
2. 安全设置期望格式；驱动拒绝某项设置时不能导致服务进程退出。
3. 在限定时间内读取至少一帧有效图像。
4. 记录实际宽、高和 FPS；未知 FPS 使用 `null`，不显示 `-1 FPS`。
5. 释放测试句柄。

无法稳定读取的虚拟摄像头不进入默认列表，并在诊断信息中记录原因。第一版仍使用索引作为实际打开参数，但界面显示设备名称、实际能力和稳定设备指纹；如果 DirectShow 名称顺序与 OpenCV 索引无法可靠对应，后续替换为按设备路径打开。

“开始预览”只打开摄像头和视频发布，不加载循迹控制。用户确认画面后点击“启动视觉处理”，才启动检测器和相关算法。

## 8. API 契约

所有响应使用统一封装：

```json
{
  "ok": true,
  "state": "previewing",
  "sessionId": "...",
  "data": {},
  "error": null
}
```

失败示例：

```json
{
  "ok": false,
  "state": "error",
  "sessionId": null,
  "data": {},
  "error": {
    "code": "camera_first_frame_timeout",
    "message": "摄像头已打开，但在 3 秒内没有收到有效画面"
  }
}
```

第一版端点：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/vision/cameras` | 返回经过首帧验证的设备列表 |
| `POST /api/vision/sessions` | 用 `cameraId` 创建预览会话 |
| `GET /api/vision/sessions/current` | 获取权威状态快照 |
| `DELETE /api/vision/sessions/{id}` | 安全停止并释放会话 |
| `POST /api/vision/sessions/{id}/processing` | 启动视觉算法 |
| `DELETE /api/vision/sessions/{id}/processing` | 停止算法并回到预览 |
| `POST /api/vision/sessions/{id}/actions` | 提交标定、轨迹和工具动作 |
| `GET /api/vision/sessions/{id}/stream.mjpg` | 当前会话视频流 |

动作响应至少包含 `actionId`、`accepted` 和当前状态。需要异步完成的操作在状态快照中返回最近结果；截图、录像开始/停止和标定完成必须返回具体结果或错误。

## 9. 网页工作区

页面分为四个区域：

1. **视频画布：** 干净视频、检测框、轨迹和标定覆盖层。
2. **会话控制：** 摄像头选择、开始预览、停止预览、启动/停止视觉处理。
3. **工具控制：** 场地标定、鱼尾框选、鱼头方向、绘制/撤销/清除轨迹、截图、录像、曝光和 CLAHE。
4. **状态面板：** 会话状态、摄像头实际分辨率/FPS、视觉循环 FPS、YOLO FPS、目标状态、标定状态、循迹状态和最后错误。

旧视频底部工具栏从正式 MJPEG 输出中删除。低频诊断信息移到状态面板；视频上只保留直接帮助空间判断的检测框、参考点和路径。

## 10. 网页覆盖层

覆盖层使用与视频元素相同的显示区域，并按以下公式换算：

```text
原始 x = clamp((指针 x - 视频内容左边界) × 原始宽 / 视频内容显示宽)
原始 y = clamp((指针 y - 视频内容上边界) × 原始高 / 视频内容显示高)
```

换算必须按实际 `object-fit` 内容区域处理，不能直接使用外层容器尺寸。覆盖层提供即时反馈：

- 场地标定显示编号 1–4、连线和闭合区域。
- 鱼尾标定在拖动时显示矩形。
- 鱼头方向显示鱼尾到点击点的箭头。
- 轨迹绘制在指针移动时立即显示折线，松开后提交服务器。
- 服务端拒绝操作时回滚该次临时覆盖并显示错误。

切换工具会显式结束旧工具状态。停止会话、会话 ID 改变或进入 `error` 时，清除所有未确认临时图形。

## 11. 视频输出与性能

Python 将可交互 UI 与视频渲染分离。正式流只生成：

- 摄像头帧。
- YOLO/标记检测结果。
- 服务端确认的轨迹和标定结果；如果网页覆盖层已能完整表现，则可关闭同类服务端绘制，避免重复。

MJPEG 第一轮采用 640×480、最高 20 FPS、JPEG 质量 50 作为默认基线。编码后的 JPEG 每帧只生成一次，所有观看者共享最新编码结果，避免每个客户端重复编码。

状态接口记录采集 FPS、处理 FPS、编码 FPS、平均 JPEG 字节数和当前观看者数量。只有在局域网和 FRP 实测仍不满足延迟要求时，再用 WebRTC/H.264 替换视频端点；画布和控制 API 不变。

## 12. 错误处理

- 摄像头打开、属性设置或首帧读取异常不得终止 Python HTTP 服务。
- 视觉应用线程退出时必须回写 `error` 或 `idle`，不能保留 `processing`。
- Go 发现 Python 不健康时返回结构化 `vision_backend_unavailable`，不把反向代理的 502 直接交给网页。
- 视频断开只进行有限次数重连；状态已非预览/处理时立即停止重连。
- 连续失败后显示明确恢复动作：“重新扫描摄像头”或“重新开始预览”。
- 任何视觉异常都触发机器鱼安全停止。

## 13. 测试与验收

### 自动测试

- 枚举排除无法读取首帧的设备，并释放所有句柄。
- 驱动拒绝格式设置时返回错误而不杀死 HTTP 服务。
- 状态机只允许合法转换。
- 旧 `sessionId` 的动作和视频请求被拒绝。
- 视觉线程异常后状态进入 `error`，网页工具禁用。
- 停止后摄像头、MJPEG、检测器和录像资源全部关闭。
- 覆盖层坐标换算覆盖等比缩放、留黑边、高 DPI 和边界裁剪。
- 轨迹拖动显示即时折线，并提交原始像素坐标。
- 同一 JPEG 编码结果可供多个客户端读取。

### 真实设备验收

1. 三个候选摄像头分别预览，名称与内容对应；不可用虚拟摄像头有明确错误或不列出。
2. 连续执行 20 次“预览→停止→切换设备”，没有设备占用残留。
3. 依次完成四点标定、鱼尾框选、鱼头方向和轨迹绘制，网页即时反馈与处理结果一致。
4. 在绘制中途停止，重启后不出现旧轨迹事件。
5. 拔出摄像头后 2 秒内进入错误状态并安全停止机器鱼。
6. 单浏览器局域网基线达到稳定 15–20 FPS，视频不持续累积延迟。
7. 两个浏览器同时观看时只执行一次 JPEG 编码。

## 14. 迁移顺序

1. 修复摄像头枚举、首帧验证和异常不退出。
2. 引入视觉状态机与 `sessionId`，保留旧端点作为短期兼容层。
3. 分离预览和视觉处理生命周期。
4. 实现网页覆盖层和结构化动作结果。
5. 删除正式视频流中的旧工具栏与冗余 HUD。
6. 改为共享 JPEG 编码并加入性能指标。
7. 删除旧端点兼容层，执行真实设备验收。

每一步都必须保持紧急停止可用。旧接口只有在前端完全切换并通过整机验收后才能移除。

## 15. 摄像头曝光结果契约

曝光调整不能把“动作进入队列”当成“硬件已经生效”。Python 执行曝光动作时必须：

1. 读取调整前的 `CAP_PROP_EXPOSURE`。
2. 请求关闭自动曝光，但不能仅凭 `VideoCapture.set()` 的布尔返回值判断硬件不支持；DirectShow 驱动可能在设置已生效时返回 `false`。
3. 写入目标曝光值，以后续硬件回读结果作为是否生效的依据。
4. 再次读取实际曝光值。
5. 实际值没有变化时返回 `exposure_not_applied`，不能返回成功。

成功结果：

```json
{
  "actionId": "...",
  "type": "camera.exposure",
  "status": "completed",
  "requestedDelta": 1,
  "previousValue": -6,
  "actualValue": -5
}
```

状态快照保存 `exposure.supported`、`exposure.auto`、`exposure.actualValue` 和最近错误。网页按钮只有在摄像头声明支持手动曝光时启用，操作期间禁用重复点击，并显示驱动返回的实际值。不同摄像头不共享曝光值；新会话必须重新读取设备状态。

## 16. ESP32 主动声明与控制器自动回连

当前电脑广播挑战、ESP32 回复身份的发现方式可以认证设备，但 ESP32 建立 WebSocket 时仍依赖 NVS 中保存的 `controllerHost`。电脑地址或网卡变化后会出现“UDP 已发现、网页无设备”的分裂状态。

新协议改为设备主动声明，控制器认证回应：

```text
ESP32                         Go 控制器
  │ discovery.announce           │
  │ deviceId + deviceNonce       │
  │ deviceProof                  │
  ├─────────────────────────────►│
  │                              │ 验证设备 HMAC 与重放窗口
  │ discovery.offer              │
  │ deviceNonce + controllerNonce│
  │ port + controllerProof       │
  ◄──────────────────────────────┤
  │ 验证控制器 HMAC              │
  │ 使用 UDP 回包来源 IP          │
  │ WebSocket /ws/device         │
  ├─────────────────────────────►│
  │       原有 WS 动态挑战认证     │
```

### 16.1 设备声明

ESP32 在 Wi-Fi 连接成功后立即发送，并每 5 秒向当前子网广播：

```json
{
  "type": "discovery.announce",
  "protocolVersion": 2,
  "deviceId": "AC:27:6E:7C:37:18",
  "deviceNonce": "随机16字节十六进制",
  "proof": "HMAC",
  "name": "机器鱼",
  "firmwareVersion": "1.2.0",
  "ip": "192.168.137.117"
}
```

证明内容：

```text
HMAC-SHA256(
  deploymentKey,
  "fish-discovery-announce-v2\n" + deviceNonce + "\n" + 标准化MAC
)
```

每次声明使用新的密码学随机 nonce。控制器只接受协议版本 2、合法 MAC、正确证明和未重复 nonce。已见 nonce 保留 30 秒；缓存按设备限制数量，防止内存增长。

### 16.2 控制器回应

控制器向声明数据包的来源 IP 和来源端口单播回应，不在正文中指定 IP：

```json
{
  "type": "discovery.offer",
  "protocolVersion": 2,
  "deviceId": "AC:27:6E:7C:37:18",
  "deviceNonce": "原值",
  "controllerNonce": "随机16字节十六进制",
  "port": 8081,
  "proof": "HMAC"
}
```

证明内容：

```text
HMAC-SHA256(
  deploymentKey,
  "fish-controller-offer-v2\n" + deviceNonce + "\n" +
  controllerNonce + "\n" + 标准化MAC + "\n" + port
)
```

ESP32 只接受与最近一个声明 nonce 匹配、设备 ID 一致、端口有效且 HMAC 正确的回应。连接目标 IP 必须使用 UDP 包的来源地址，不能信任 JSON 提供的地址。

### 16.3 WebSocket 与回退行为

- 有效 offer 到达后，ESP32 立即断开错误目标并连接来源 IP 的 `/ws/device`。
- WebSocket 仍执行现有 `fish-websocket-v1` 随机挑战认证，发现 offer 不能替代连接认证。
- 控制器断开后，ESP32 恢复每 5 秒主动声明并接受新的有效 offer。
- NVS 中保存的 `controllerHost` 仅作兼容回退：连续 30 秒未收到有效 offer 时才尝试，不能阻止继续广播。
- offer 只更新内存中的当前目标，不自动写 NVS，避免网络切换频繁磨损闪存。
- 同一设备收到多个合法控制器 offer 时，优先使用最先完成 WebSocket 认证的连接；成功后在连接存活期间忽略其他 offer。
- UDP 声明或 offer 解析失败不会改变当前运动状态；WebSocket 失联规则仍立即安全停止。

### 16.4 兼容与验收

Go 在迁移期同时保留版本 1 的电脑主动广播，用于发现旧固件，但只有版本 2 固件具备自动控制器回连能力。网页诊断区区分：`discovered_v1`、`offered_v2`、`websocket_connecting`、`online` 和认证失败。

验收必须覆盖：电脑 IP 变化、Wi-Fi 重连、多网卡、错误 HMAC、重复 nonce、伪造正文 IP、两个控制器同时回应、控制器重启和 30 秒兼容回退。任何情况下，未完成 WebSocket 动态认证的设备都不能进入可控制列表。
