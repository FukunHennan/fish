# 机器鱼局域网中央控制系统设计

**状态：** 已确认  
**日期：** 2026-08-24  
**目标平台：** ESP32-C3、macOS、Windows

## 1. 目标与拓扑

机器鱼主动连接同一个外部路由器，并与局域网中长期运行的中央控制器保持连接。用户在中央控制器提供的网页中控制单台、多台、分组或全部机器鱼。系统先支持 3 台，并可扩展到约 30 台。

```text
远程或局域网浏览器
        │ HTTPS / FRP
        ▼
Mac 或 Windows 中央控制器
  ├─ 管理网页、设备状态、命令路由
  ├─ SQLite、固件和 OTA 任务
  └─ 局域网 WebSocket + HTTP
        ├─ 机器鱼 A
        ├─ 机器鱼 B
        └─ 机器鱼 C……机器鱼 30
```

日常控制时浏览器只访问中央控制器。中央控制器根据 MAC 找到设备的活动连接并转发命令，浏览器不需要知道机器鱼的动态 IP。只有首次配网时，手机才直接连接机器鱼的临时热点。

## 2. 技术选型

- 固件：PlatformIO、Arduino Framework、Seeed XIAO ESP32-C3。
- 实时通信：设备与中央控制器使用 WebSocket。
- 固件传输：设备通过局域网 HTTP 下载固件。
- 中央控制器：Go、SQLite。
- 管理网页：React、Vite、TypeScript。
- 发布：网页嵌入 Go 可执行文件，分别生成 Windows 和 macOS 程序。

## 3. 身份、配网与连接

设备使用大写冒号格式的 Wi-Fi MAC 作为稳定 ID。MAC 不是密码；第一版由所有机器鱼和控制器共同持有一个部署密钥，后期可升级为每设备独立密钥。部署密钥保存在控制器本地配置文件中并加入 `.gitignore`，PlatformIO 构建固件时自动读取同一配置并注入固件，用户不需要手工输入设备令牌。

NVS 保存路由器 SSID、密码、中央控制器地址和显示名称，不保存人工录入的设备令牌。启动后优先以 STA 模式连接路由器。没有配置或连续 60 秒连接失败时，设备建立 `Fish-Setup-XXXXXX` 临时热点，并在 `192.168.4.1` 提供配网页。提交有效配置后保存并重启。串口命令 `CLEAR_CONFIG` 可清除配置。

第一版在路由器中为中央控制电脑设置 DHCP 地址保留，并在配网页填写固定局域网 IP 和端口，不依赖 mDNS。

## 4. 局域网发现与动态身份验证

Go 控制器每 5 秒枚举所有有效 IPv4 局域网接口，并向各接口广播 UDP 设备信息请求。请求包含协议版本、随机请求 ID 和使用密码学安全随机数生成的 nonce。机器鱼收到请求后立即单播回复 MAC、IP、名称、固件版本、RSSI、运行时间和完整运动状态。

发现证明采用动态挑战应答：

```text
proof = HMAC-SHA256(
  部署密钥,
  "fish-discovery-v1" + "\n" + nonce + "\n" + 标准化MAC
)
```

WebSocket 使用域 `fish-websocket-v1`，消息拼接格式与发现协议相同。域、nonce 和 MAC 之间固定使用单个换行符，避免跨语言实现产生歧义。

Go 使用标准库 `crypto/rand`、`crypto/hmac` 和 `crypto/sha256` 验证证明。ESP32 使用 Arduino ESP32 框架自带的 mbedTLS。nonce 只能使用一次并设置短期有效时间，过期、重复或 HMAC 错误的回复全部丢弃并写入安全日志。

UDP 发现只负责发现、认证和基础状态快照，实时状态与控制继续使用 WebSocket。WebSocket 注册也采用服务端随机挑战和动态 HMAC 证明，不再上传固定令牌。Go 使用成熟的 `github.com/gorilla/websocket`，删除项目内自写的 WebSocket 帧处理器。

网页只显示当前通过认证且 WebSocket 在线、可以立即接受控制命令的机器鱼。普通局域网设备、仅 UDP 可见但 WebSocket 未连接的机器鱼均不进入网页设备列表；WebSocket 断开后立即移除设备卡片，不保留离线卡片。Go 仍可把发现异常写入诊断日志。

## 5. 协议与安全停止

设备注册内容包括协议版本、MAC、动态 HMAC 证明、名称、IP、固件版本和能力。认证成功后才接受控制消息。运动命令包含请求 ID、模式、频率、幅度和偏置，设备返回相同请求 ID 的结果。

双方每秒发送心跳。设备 2 秒没有收到有效控制器心跳时立即将尾舵归中停止；中央控制器 3 秒没有收到设备消息时标记离线。重连采用带上限的退避策略，成功后重新注册并上报完整状态。

频率与幅度独立于动作方向，方向切换不能恢复默认值。`STOP` 表示真正归中停止；缓慢摆尾使用独立 `IDLE` 模式。

## 6. OTA 与公网边界

网页上传 `.bin` 后，中央控制器计算 SHA-256 并保存不可变记录。设备通过 WebSocket 收到任务，再通过局域网 HTTP 下载。固件头、字节数和 SHA-256 全部通过后才切换启动分区。默认最多同时升级 3 台，并建议先升级一台试点。

第一阶段不承诺启动后自动回滚。下载、写入或重启前校验失败时不切换分区。真正的 bootloader 自动回滚后续单独实现。

ESP32 第一阶段必须预留可版本化的 OTA 指令、进度上报、结果上报和安全停止接口。网页端的固件上传、任务编排和正式 OTA 操作页面可以在后续逐步加入，不能因此再次修改设备身份或基础消息封装。

FRP 只转发带登录和 HTTPS 的管理入口。设备 WebSocket 和固件下载入口只监听局域网。日志不得包含 Wi-Fi 密码、管理员密码、设备令牌或会话令牌。

## 7. 文件结构

```text
fish/
├─ firmware/       ESP32 固件
├─ controller/     Go 中央控制器
├─ web/            React 管理网页
├─ protocol/       通信协议
├─ scripts/        构建脚本
└─ docs/           设计、计划和部署文档
```

固件拆分为运动控制、配置存储、网络管理、配网页、设备身份、控制器客户端和 OTA 管理模块；`main.cpp` 只负责组装和循环调度。

## 8. 五阶段开发顺序

开发作为一个连续项目推进，不要求每个内部模块单独交付审核。每个阶段以用户能够验证的系统能力为边界。

### 第一阶段：ESP32 完整设备能力

ESP32 必须先完成后续所有任务需要的设备端能力，包括：

- 主动连接路由器、配网门户、NVS 和控制器重连。
- MAC 身份、令牌注册、心跳、状态和故障上报。
- 前进、左转、右转、停止、待机、频率、幅度和偏置控制。
- 视觉控制会话、递增序号、误差、速度、曲率、制动和超时停止。
- 控制权模式：停止、网页手动和视觉控制。
- 每条指令的请求 ID、参数验证、执行结果和状态回传。
- OTA 开始、进度、结果和安全停止接口；网页 OTA 可后续实现。

第一阶段结束时，ESP32 协议不应再因第二至第四阶段的常规功能迁移而发生破坏性修改。

### 第二阶段：简单 Web 全功能测试

使用简单、非正式设计的网页验证 ESP32 全部功能：设备上线、状态、手动运动、参数、视觉指令模拟、控制权切换、失联停止、错误反馈和 OTA 接口占位。此阶段关注功能正确性，不进行正式 UI 设计。

### 第三阶段：Web 显示视觉内容

把 Python 视觉服务接入中央控制器，使同一 Web 页面能够显示实时视频、检测叠加、视觉状态和主要遥测。此阶段以“看得到且状态正确”为目标，不迁移全部操作。

### 第四阶段：Web 复现 VISION 全部功能

将当前 VISION 的水池标定、鱼尾标定、鱼头方向、路径绘制、循迹启停、转圈标定、录像、截图、CSV、参数配置、日志和安全停止完整迁移到 Web。本地 OpenCV 窗口保留为调试备用入口。

### 第五阶段：正式 UI 设计

在全部功能已经可测试后，再完成信息架构细化、视觉风格、响应式布局、交互反馈、无障碍和正式组件设计。已选择的视频工作台方案 A 作为设计起点，但不提前限制第二至第四阶段的测试界面。

## 9. 统一 Web 视觉平台

视觉功能必须进入与设备管理相同的 Web 控制台，不再建立独立视觉网站。Python 保留摄像头、YOLO、HSV、ArUco、坐标转换、路径导航和控制量计算；Go 负责统一网页、配置、设备连接、控制权、日志和持久化。

```text
浏览器统一 Web 控制台
  ├─ 设备与手动控制
  ├─ 实时视觉画面
  ├─ 标定与路径绘制
  ├─ 视觉循迹
  ├─ 参数、日志和数据
  └─ 固件升级
          │
          ▼
Go 中央控制器
  ├─ 网页 API 与实时状态
  ├─ SQLite 配置和事件
  ├─ 设备 WebSocket
  └─ Python 内部通信
          │
          ▼
Python 视觉服务
  ├─ USB 摄像头
  ├─ YOLO、HSV、ArUco
  ├─ 路径引导和视觉控制量
  └─ 可选 OpenCV 调试窗口
```

正式操作入口是 Web。OpenCV 本地窗口通过 `--debug-window` 开启，仅作为调试备用入口。它与 Web 共享同一份运行状态，且不能绕过 Go 直接控制设备。

## 10. 第一版视觉范围

第一版只支持单摄像头、单目标机器鱼的视觉闭环。设备列表可以包含多台设备，但同一时间只能选择一台作为视觉目标，只能存在一个视觉控制会话。多目标识别、身份保持和同时控制多条鱼不属于第一版范围。

第一版继续使用 VISION 已有的 MJPEG 能力传输处理后视频，目标为约 20～30 FPS。控制状态、遥测和配置通过独立 WebSocket 传输，不能依赖视频流作为控制通道。

浏览器需要支持：

- 点击水池四角进行手动标定。
- 使用 ArUco 自动标定并显示稳定状态。
- 在视频上框选鱼尾颜色区域。
- 点击鱼头方向。
- 使用鼠标或触摸绘制、撤销和清除路径。
- 启动、停止和紧急停止视觉循迹。
- 将显示坐标准确换算回原始摄像头坐标。

Web 和调试窗口对标定、路径等编辑操作使用服务端编辑锁。同一时间只有一个入口能编辑，另一个入口保持只读。

## 11. Web 信息架构

采用已确认的“视频工作台”布局：

- 顶部显示系统状态、当前设备和全局紧急停止。
- 左侧显示设备列表和功能导航。
- 中间以实时视频为主体，承载标定、路径绘制和检测叠加。
- 右侧显示当前任务、控制参数和视觉运行指标。

左侧导航包含：

```text
设备
视觉工作台
视觉配置
控制参数
录像与数据
固件升级
系统日志
```

视觉工作台负责高频操作，其他页面承载低频配置，避免主画面拥挤。

## 12. 配置与信息查看

Go 是配置的唯一持久化入口，配置保存到 SQLite。Python 启动时从 Go 获取配置，并通过内部 WebSocket 接收变更。用户不再直接编辑 `config.py`。

配置按生效方式分类：

- 即时生效：YOLO 置信度、检测间隔、HSV、画面增强、控制频率和 PID。
- 停止循迹后生效：目标设备、摄像头、分辨率、场地尺寸和控制模式。
- 重启视觉服务后生效：模型文件、监听端口、CUDA/CPU 和数据目录。

Web 至少显示：

- 设备名称、MAC、IP、在线状态、固件版本和 RSSI。
- 摄像头 FPS、YOLO FPS、控制频率和端到端延迟。
- 目标位置、速度、航向、置信度和跟踪来源。
- 离轨误差、目标距离、曲率、转向量和制动请求。
- 标定状态、视觉会话、编辑锁和停止原因。
- Go/Python 服务状态、CPU/GPU 模式和错误日志。
- 录像、截图、CSV 和模型文件信息。

## 13. 控制权与故障处理

控制权优先级为：

```text
紧急停止 > 网页手动控制 > 视觉循迹 > 安全停止
```

- 紧急停止立即废止视觉会话和所有排队命令。
- 视觉循迹运行时锁定普通手动方向按钮，退出视觉模式后才能手动控制。
- 切换目标前必须停止当前目标。
- 浏览器关闭不自动终止服务端任务，重新打开页面后继续显示真实状态。
- Python 断开、摄像头失帧、目标丢失、标定失效或视觉控制超时都会触发停止。
- Go 断开时，由 ESP32 的 2 秒本地超时完成最终安全停止。
- 所有启动、停止、参数修改、标定、目标切换和异常写入事件日志。

## 14. VISION 整合边界

保留 VISION 的感知、导航、录像、MJPEG 和安全状态机。替换其 `RoboFishComm` 直接访问 `192.168.4.1` 的旧 HTTP 传输，使其通过 Go 中央控制器控制指定 MAC。

旧 `/control` 和 `/vision_pid` 协议不再作为正式链路。中央控制器提供视觉会话接口，消息至少包含目标设备、会话 ID、递增序号、横向误差、目标距离、速度、曲率和制动请求。ESP32 需要新增视觉控制模式，并在视觉命令超时时停止。

## 15. 视觉平台验收

第一版必须完成以下闭环：

1. Web 显示实时处理后视频。
2. Web 完成水池、鱼尾和方向标定。
3. 从在线设备中选择一台视觉目标。
4. 在视频上绘制路径并启动循迹。
5. 实时查看误差、速度、置信度和控制状态。
6. Web 停止、本地调试窗口停止和故障自动停止均有效。
7. 重启 Go 和 Python 后，配置和标定可以恢复。
8. Python 不可用时，设备管理和手动控制仍可使用。
