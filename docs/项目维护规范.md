# 项目维护规范

> 当前使用范围：本项目仅面向内部研发和受控环境。暂不考虑公网攻击、商用部署、密钥保护及相关安全加固，也不保留未来商用/公网部署前检查清单。维护工作集中于设备功能、控制可靠性、视觉算法、视频链路、异常恢复、实机验证和文档一致性。

## 目录与入口

| 路径 | 用途 |
| --- | --- |
| controller/internal、controller/cmd | Go 服务与入口 |
| controller/frontend/src | 正式 GUI 源码 |
| controller/frontend/gui-redesign-demo | 兼容开发入口，仍连接真实设备；暂时保留 |
| controller/internal/web/dist | 前端构建输出，由 Go 嵌入 |
| vision | Python 摄像头采集、共享识别及控制逻辑 |
| firmware | ESP32 固件与固件测试 |
| protocol | 跨模块消息协议 |
| config、scripts | 配置模板与启动/部署脚本 |
| docs | 使用、维护和架构文档 |
| design/gui/prototypes | 可运行设计原型 |
| design/gui/archive | 不再使用的历史设计材料 |

推荐开发入口：在 `controller/frontend` 运行 `npm run dev`。8098 为开发 GUI，8081 为 Go 提供的正式 GUI；两者使用同一套正式源码。兼容入口仍保留，不能同时启动两个 8098 进程。

前端构建后再构建 Go。正式服务路径由 systemd ExecStart 确认。只修改源码或构建 dist 不会自动替换已运行二进制。文档和历史原型整理不需重启设备服务。

模型、校准、诊断记录、运行配置不按“无引用文件”直接清理。每次文件迁移检查源码引用、脚本工作目录及文档链接，保留已有用户改动。生成输出按现有 .gitignore 管理，不随手把本地数据提交到仓库。

## 已确认的产品方向

- 所有用户使用服务器上的同一摄像头；优先匹配 Global Shutter Camera，不固定 video 编号。
- 原始画面、识别结果和目标编号共享，避免每个用户重复跑识别。
- 本机预览、页面选择、显示叠加、轨迹编辑和控制参数应按用户或工作会话隔离。
- 绑定关系统一管理，禁止一个识别目标同时绑定多条鱼；修改绑定需校验对应设备控制权。
- 多个用户可控制不同鱼，同一条鱼只有一个持有者。
- 摄像头切换、曝光、模型及共享识别启停属于服务器级设置，目标是由管理员管理。

## 当前实现与差距

已实现：本机预览关闭不删除共享视频会话；按名称优先选择全局快门摄像头；普通运动请求有控制权机制。

尚未完成：视觉后端仍以单会话、单目标为主；绑定冲突约束、多鱼并行控制任务、个人轨迹与显示隔离、共享设置的完整后端管理员权限都需要进一步改造和验证。不能以隐藏按钮或浏览器状态代替后端权限隔离。

后续实施顺序：先建立用户/设备/识别目标绑定模型与权限测试，再将每条鱼的控制任务从共享采集识别中拆开；最后接入 GUI 并做两账号、两设备并发验证。验证需涵盖一用户退出或停止不会误停另一用户、旧控制者不能继续发送运动、目标丢失能停止对应鱼。

## 多鱼手动控制（2026-09-04）

- 一个账号可以同时持有多条鱼；领取新鱼不释放已有鱼。设备归属与运动超时分离：超时停止运动但保留归属，管理员全局急停也保留归属。
- 只有持有者主动释放或管理员强制释放会解除用户归属。开启认证时，归属保存到用户数据文件旁的 `.reservations.json`；服务重启后保留持有者，浏览器需明确恢复控制，不恢复运动。
- 单条鱼的命令仍校验账号和浏览器控制会话；其他浏览器的普通停止命令不能干扰持有者。管理员全局急停使用独立接口。
- 手动控制右栏的“自定义按键”可为每条鱼设置前进、左右转和停止键。启用“多鱼键盘控制”后，该鱼无需保持选中也可接受本窗口按键。按键仅对已明确领取的鱼生效。
- 同一组按键可以联动多条已启用的鱼；独立操控可分别设置 WASD、IJKL 等键组。空格停止键盘目标，切到后台或失去窗口焦点停止本窗口键盘运动。
- 按键和手动运动参数按账号保存在当前浏览器，不跨电脑同步。视觉自动控制仍是单目标架构，个人轨迹、绑定和自动任务的完整隔离尚未完成。

验证：Go 全套测试及前端 37 项测试、生产构建；使用模拟设备验证多鱼、外部停止拒绝、超时保留归属、重启恢复归属。未向实体鱼发送测试运动。

摄像头排除策略位于 `vision/camera_policy.py`：项目永久排除名称包含 `USB2.0 FHD UVC WebCam` 的摄像头，枚举不探测、列表不展示、HTTP 选择请求和实际打开均拒绝。按名称及实时设备节点解析，不固定排除索引 0；不会禁用系统其他应用使用该摄像头。Global Shutter Camera 保留可用。

## 采集与观看分辨率（2026-09-04）

服务器采集默认 2592×1944、请求 30 FPS，使用 MJPEG 摄像头格式；YOLO 输入尺寸默认 2592（模型内部仍会按比例及步长对齐）。可通过服务环境变量 `FISH_CAPTURE_WIDTH`、`FISH_CAPTURE_HEIGHT`、`FISH_YOLO_IMGSZ` 修改，需重启服务。这些是服务器设置，不由观看者修改。

每个 WebRTC 连接独立选择 smooth（640×480 边界）、hd（1280×960 边界，GUI 默认）、full（1920×1440 边界）；保留比例、不放大小图，不改识别原图。GUI 视频设置中的“本机清晰度”仅影响当前观看连接，当前为手动选择，并非自动网络自适应。选择保存在当前页面会话中。

视频点击沿用 `toVideoPoint`，从实际显示尺寸映射回服务端原始 frame 尺寸；不以传输尺寸作为识别坐标。

验证：独立高低清连接共用原图测试、WebRTC/API 测试与前端测试通过。实机确认采集 2592×1944；当前曝光下预览约 15 FPS，不能将请求 30 FPS 当作实测帧率。此次没有开启视觉运动，也未测量实际高分辨率 YOLO 推理性能。

### 分辨率修正（2026-09-04，覆盖上节默认值）

依据用户提供的 AR0234 规格与实物 UVC 模式表，默认采集改为 1920×1080、请求 30 FPS（MJPEG），YOLO 输入尺寸改为 1920。设备模式表未提供 1920×1200；不能以驱动提供 2592×1944 推断传感器原生像素。观看清晰度仍按连接独立设置。

重启后实机确认 frame=1920×1080，当前曝光下约 15 FPS；YOLO 未启动，尚未验证此次调整的识别速度及稳定性。

## 共享识别区域裁剪

管理员可在视频设置 → 识别区域裁剪中框选矩形、应用或恢复全画面。需先停止识别/循迹；应用将重建预览会话、清除旧会话目标绑定，应重新检查场地和方向标定。设备用户归属不因裁剪释放。

裁剪参数为原始画面的归一化矩形，保存到 `CACHE_DIR/camera-crop.json`。摄像头 read/snapshot 在交给显示和识别前执行相同裁剪，并同步逻辑画面尺寸；缩放观看视频仍映射到裁剪后的逻辑坐标。重复框选相对当前裁剪区域组合，最小宽高为原图的 5%。当前项目只有一个允许使用的摄像头，该配置为服务器级共享配置。

Go 对 `/api/vision/crop` 的写请求执行管理员校验，Python 为摄像头生命周期修改串行化，避免裁剪和识别启动并发。裁剪功能不执行透视纠正，不自动恢复运动。测试覆盖裁剪像素、保存/恢复、非法范围和预览会话重建。

## 控制权限修复

重启恢复的归属 clientId 为空，前端必须显示待恢复，不得当作当前浏览器已领取；用户 ID 与浏览器 ID 均匹配后才启用运动。普通释放按钮必须显式传 false，避免 React 点击事件被当作 force 参数；请求解析失败返回 400。完整操作说明见 [多用户控制与视频使用说明](多用户控制与视频使用说明.md)。

## 登录与性能维护

新登录会话以令牌摘要持久化到用户文件旁 `.sessions.json`，有效期不变；登录可跨重启保留，设备控制会话仍需恢复。YOLO 设备选择已修正为按 CUDA 可用性使用 GPU，而非按模型初始加载位置判断。main.jsx 的旧单鱼键盘执行链已移除。实测与未解决项见 [维护记录](2026-09-04会话与性能维护.md)。
