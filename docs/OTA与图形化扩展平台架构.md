# 机器鱼 OTA 与图形化扩展平台架构

更新时间：2026-09-04

## 1. 定位

本项目不是通用 Arduino IDE，而是机器鱼控制板的专用开发、升级和调试工作台。

核心关系是：

```text
设备选择
  → OTA 更新固件与能力
  → Mixly 风格积木编程
  → 在线运行或下载程序
```

第一阶段只安装经过描述、校验和授权的固件包，不直接执行未知脚本或动态机器码。

这里的图形化编程采用 Mixly 的交互思路：以 Blockly 积木替代复杂文本代码，并根据目标硬件提供相应功能块。Mixly 本身也采用 Blockly 作为图形化编程引擎。 

面向五年级学生的程序默认是“临时程序”：它只能调用底层固件公开的安全能力，不修改底层固件，也不写入控制板的固件区域。程序停止、设备断开或控制板重启后，临时运行状态自动清除。

## 2. 总体结构

```text
机器鱼工作台（React）
  ├── 设备列表、能力和状态
  ├── 图形化编程（Mixly 风格）
  ├── 固件仓库和版本选择
  ├── OTA 任务、进度和日志
  ├── 设备设置、校准和诊断
              │ HTTP / WebSocket
              ▼
Go 控制器
  ├── Device Registry       设备注册与能力目录
  ├── Artifact Store        固件与扩展包仓库
  ├── Release Manager       版本与兼容性
  ├── OTA Scheduler         任务、队列、重试和批量升级
  ├── Device Adapter        现有设备协议适配
  ├── Audit Log             操作与结果记录
  └── Safety Gate           权限、停止运动和升级前检查
              │ 已认证设备 WebSocket
              ▼
ESP32 控制板
  ├── OTA Agent             下载、校验、写入和重启
  ├── Boot / Rollback       双分区启动与失败回滚
  ├── Capability Provider   上报硬件能力和版本
  └── Runtime               运动、灯光、传感器和扩展运行时
```

浏览器不直接连接 ESP32。设备命令、控制权、部署密钥和 OTA 任务均由 Go 控制器统一管理。

## 3. 底层固件与临时程序

系统分成两个互相隔离的层：

```text
底层固件（稳定、受保护）
  ├── 电机 / 舵机驱动
  ├── 传感器驱动
  ├── 网络、认证和 OTA Agent
  ├── 安全限幅、急停和断线保护
  └── 对外提供能力 API

临时程序（学生可编辑）
  ├── 节点 / 积木流程
  ├── 条件、循环和计时
  ├── 运动、灯光和传感器调用
  └── 运行时状态
```

临时程序的规则：

- 只调用底层固件提供的白名单能力。
- 不允许修改舵机底层驱动、网络认证、OTA Agent 或安全限幅。
- 默认保存在电脑端项目文件中，运行时发送到控制器内存。
- 不把学生程序写入固件分区，不通过 OTA 发布。
- 运行前由控制器检查节点、参数、设备能力和运行时长。
- 停止、急停、断线、页面关闭或控制板重启时，清除运行实例并发送停止命令。
- 保存项目不等于写入控制板。

因此，“OTA 升级固件”和“运行临时程序”是两个完全不同的任务。OTA 需要管理员权限；临时程序只获得目标设备的短时控制权。

## 4. 模块边界

### 3.1 React 工作台

建议页面：

- **设备**：在线状态、硬件型号、固件版本、能力和网络信息。
- **编程**：Mixly 风格积木编辑器、代码预览、运行和下载。
- **固件**：上传包、查看 manifest、校验信息和发布状态。
- **升级任务**：选择目标、预检查、执行、进度、结果和重试。
- **设备设置**：名称、舵机中位、传感器配置和诊断。
- **编程**：根据设备能力动态显示机器鱼积木。

工作台只展示状态和发起操作，不保存部署密钥，不自行判断 OTA 成功。

### 3.2 Go 控制器

Go 负责：

- 保存固件和扩展包及其 manifest。
- 校验大小、摘要、签名、硬件型号和版本兼容性。
- 为每台设备建立独立 OTA 任务。
- 升级前停止运动并等待设备状态确认。
- 控制并发升级、重试和取消。
- 记录操作人、设备、包版本、阶段和错误码。
- 服务重启后将未完成任务恢复为“待核查”，不伪造成功。

建议后续增加：

```text
controller/internal/
  ota/       包仓库、兼容性、任务状态机和调度
  device/    设备能力目录
  audit/     OTA 操作记录
```

新增模块应与现有 `web`、`hub` 的职责一起确认，避免同一设备状态被重复保存。

### 3.3 ESP32 固件

保留当前 `ControllerClient` 的连接和认证职责，逐步把升级逻辑收敛为 OTA Agent：

1. 接收升级准备信息。
2. 检查大小、摘要、签名和目标硬件。
3. 停止运动并进入升级状态。
4. 下载到备用 OTA 分区。
5. 校验后写入启动标记并重启。
6. 启动新固件并上报版本。
7. 健康检查失败时回滚。

OTA 失败不能破坏设备身份配置。设备重连后必须重新注册，不能沿用旧连接状态。

## 5. OTA 与 Mixly 编程的结合

两者的职责要明确区分：

| 能力 | OTA | Mixly 风格编程 |
| --- | --- | --- |
| 作用 | 更新设备固件、资源和能力 | 编排机器鱼的行为 |
| 频率 | 偶尔执行 | 高频编辑和运行 |
| 风险 | 可能影响设备启动 | 必须可暂停、停止和恢复 |
| 结果 | 新固件重新注册并上报能力 | 程序运行状态和设备反馈 |
| 目标 | 控制板或设备组 | 一台或多台已选择设备 |

推荐用户流程：

```text
连接机器鱼
  → 读取硬件型号、固件版本和 capabilities
  → 若能力不满足，提示安装匹配固件
  → OTA 升级并等待设备重新注册
  → 打开“编程”
  → 根据 capabilities 加载积木
  → 生成程序并进行安全检查
  → 在线运行 / 暂停 / 停止 / 下载
```

编程页面的主布局：

```text
左侧：积木分类
中间：积木工作区
右侧：设备、程序属性和运行状态
底部：生成代码 / 指令预览 / 日志
顶部：设备选择、固件版本、能力状态、运行控制
```

积木分类建议：

- **事件**：启动、按钮、收到消息。
- **运动**：前进、后退、左转、右转、停止、设置频率和幅度。
- **时间**：等待、持续执行。
- **逻辑**：如果、重复、等待直到。
- **变量**：设置变量、读取变量。
- **传感器**：距离、光照、电池、IMU 等，按设备能力显示。
- **灯光**：RGB 颜色、亮度、状态指示。
- **安全**：停止、急停、连接丢失处理。

程序执行不应绕过现有控制链路。第一版由 Go 控制器解释程序并通过每台设备自己的发送队列执行，因此可以继续复用控制权、运动超时和急停机制。

## 6. 包模型

未来所有可安装内容都用 manifest 描述。第一版可以只支持 `firmware`，但数据结构应预留扩展空间。

```json
{
  "packageType": "firmware",
  "packageId": "fish-board-firmware",
  "version": "1.4.0",
  "hardware": ["xiao-esp32c3-fish-v1"],
  "protocolVersion": 1,
  "minBootloaderVersion": "1.0.0",
  "capabilities": ["motion", "battery", "status-rgb", "ota"],
  "file": {
    "name": "fish-board-1.4.0.bin",
    "size": 524288,
    "sha256": "..."
  },
  "releaseChannel": "stable",
  "signature": {
    "algorithm": "ed25519",
    "value": "..."
  }
}
```

包类型规划：

| 类型 | 阶段 | 用途 |
| --- | --- | --- |
| `firmware` | 第一阶段 | 完整控制板固件 |
| `resource` | 预留 | 动作参数、标定模板和资源 |
| `extension` | 预留 | 传感器、外设和动作描述 |
| `program` | 后续 | 图形化程序或中间指令 |

传感器和动作扩展优先通过固件内置能力、配置包和版本化协议实现，而不是立即引入动态插件代码。

## 7. OTA 任务状态机

```text
DRAFT
  → PRECHECKING
  → READY
  → STOPPING
  → DOWNLOADING
  → VERIFYING
  → INSTALLING
  → REBOOTING
  → VERIFYING_DEVICE
  → SUCCEEDED
```

异常状态：

```text
PRECHECK_FAILED
DOWNLOAD_FAILED
SIZE_MISMATCH
HASH_MISMATCH
SIGNATURE_INVALID
NO_SPACE
INSTALL_FAILED
DEVICE_RECONNECT_TIMEOUT
ROLLBACK
CANCELLED
```

批量升级是多个独立设备任务的集合，不能用一个批量结果覆盖单台设备的失败。

升级前至少检查：

- 操作者是否为管理员。
- 设备是否在线并完成认证。
- 设备是否声明 `ota` 能力。
- 固件硬件型号、协议版本和 Bootloader 版本是否匹配。
- 设备是否正在被视觉或其他用户控制。
- 设备是否已停止并确认当前运动状态。
- 固件大小是否小于可用 OTA 分区。

## 8. 协议演进

当前协议已经支持 `ota.start`、文件大小和 SHA-256。第一步保持兼容：

```json
{
  "command": "ota.start",
  "payload": {
    "sha256": "...",
    "size": 524288,
    "name": "机器鱼1号"
  }
}
```

Go 先把现有同步式 OTA 包装成可追踪任务。后续增加准备、进度和最终确认：

```json
{
  "command": "ota.prepare",
  "payload": {
    "taskId": "ota-20260904-001",
    "packageType": "firmware",
    "version": "1.4.0",
    "size": 524288,
    "sha256": "...",
    "signature": "..."
  }
}
```

设备上报：

```json
{
  "type": "ota.progress",
  "taskId": "ota-20260904-001",
  "state": "DOWNLOADING",
  "written": 262144,
  "total": 524288,
  "version": "1.4.0"
}
```

`command.result` 仍表示命令处理结果；OTA 最终成功必须以设备重启后的注册版本和健康状态为准。

## 9. 图形化编程接入

积木绑定设备能力，而不是绑定固定引脚：

```text
设备能力 manifest
  → 积木目录
  → 中间指令 / 程序包
  → 控制器校验
  → 在线执行或下载执行
```

例如设备声明 `motion` 后显示前进、转弯和停止积木；声明 `ambient-light` 后显示环境光积木。

执行分两期：

1. **在线执行**：Go 解释程序，逐条通过现有设备队列发送。
2. **离线执行**：未来将签名后的 `program` 包下载到控制板，由固件运行时执行。

第一期优先在线执行，直接复用控制权、超时停止、日志和急停机制。

## 10. 安全原则

- 浏览器永远不接触部署密钥。
- OTA 只允许管理员发起。
- 上传和下载都限制包大小。
- SHA-256 用于完整性校验，签名用于来源和授权校验。
- 升级前停止运动，升级期间拒绝普通运动命令。
- 断网、失败和重启进入明确的失败或待核查状态。
- 不把“控制器已发送”当作“设备已升级成功”。
- 日志不记录密钥。

## 11. 实施顺序

### 阶段一：统一现有 OTA

- 建立 manifest 和 OTA 任务模型。
- 将现有固件上传、摘要计算和 `ota.start` 纳入统一服务。
- GUI 增加固件详情、目标设备和单台任务状态。
- 保持当前 API 和设备协议兼容。

### 阶段二：可靠升级

- 增加硬件型号和能力字段。
- 增加异步进度、重启后确认和任务持久化。
- 增加签名、失败重试和回滚验证。

### 阶段三：扩展包

- 支持资源包、动作参数包和传感器描述包。
- 建立扩展依赖和版本兼容规则。
- 从能力 manifest 生成 GUI 设置项和图形化积木。

### 阶段四：Mixly 风格图形化编程

- 引入 Blockly。
- 建立机器鱼专用积木分类。
- 先在线解释执行，再评估离线程序包。

## 12. 当前不做

- 不让浏览器绕过 Go 直接连接 ESP32。
- 不在没有签名和回滚验证前支持未知第三方固件。
- 不把动态插件代码直接写入 ESP32 并执行。
- 不因 OTA 页面存在就宣称已经完成实机升级验证。
